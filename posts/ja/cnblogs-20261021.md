### 第 7 章 Skills：再利用できる Agent の能力パッケージ

#### Skills のディレクトリ構成

```
skills/
└── langgraph-docs/
    ├── SKILL.md              # Required: metadata + instructions
    ├── scripts/              # Optional: executable scripts
    │   └── fetch_docs.py
    ├── references/           # Optional: detailed docs
    │   ├── api-patterns.md
    │   └── style-guide.md
    └── assets/               # Optional: templates, data files
        ├── report-template.md
        └── schema.json
```

| ディレクトリ  | 用途                                                   | 読み込むタイミング                                                       |
| ------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| `SKILL.md`    | メタデータ + 中核となる指示                            | メタデータは起動時にプロンプトに入る。本文は Agent が必要に応じて読む   |
| `scripts/`    | 実行可能なスクリプト（Python、Bash、JS など）          | 指示に従って Agent が必要なときに実行する                                |
| `references/` | 詳しい参考資料（API パターン、スタイルガイドなど）     | Agent が詳しい情報を必要としたときに読む                                 |
| `assets/`     | テンプレート、データファイル、schema などの静的リソース | Agent が必要なときに読む                                                 |

#### `SKILL.md` の構成

YAML frontmatter と Markdown の本文（指示）に分かれる

**YAML frontmatter**


| フィールド    | 必須 | 説明                                                                                       |
| ------------- | ---- | ------------------------------------------------------------------------------------------ |
| name          | Yes  | 小文字、数字、ハイフンで構成し、1〜64 文字。親ディレクトリ名と一致させる必要がある。      |
| description   | Yes  | Skill の機能と使う場面を説明する。最大 1024 文字。                                         |
| license       | No   | ライセンス名                                                                               |
| compatibility | No   | 実行環境の要件（ネットワークアクセスや特定の CLI ツールが必要など）。最大 500 文字。       |
| metadata      | No   | 任意のキーと値（author、version、entrypoint など）                                         |
| allowed-tools | No   | 事前に許可するツールのスペース区切りリスト                                                 |

**description は最も重要なフィールド**

- よい description：具体的で、起動する条件がはっきりしている
- 悪い description：あいまいで、起動のきっかけがない

悪い description は 2 つの問題を招く。使うべきときにマッチしない（取りこぼし）、使うべきでないときに誤って起動する（誤検出）

#### Progressive Disclosure：段階的な読み込み

Skills は内容を一度にすべてモデルに渡すわけではない。そうするとコンテキストがノイズでいっぱいになってしまう。そこで段階的な読み込みでは Skills を 3 層に分け、必要になったときに少しずつモデルに渡す。

| 層                    | 読み込む内容                                        | 読み込むタイミング                                         | 処理するもの                                 |
| --------------------- | --------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------- |
| Level 1: Metadata     | `name` + `description` + ファイルパス               | Agent の起動時に、見つかった Skills のメタデータを読み込む | `SkillsMiddleware`                           |
| Level 2: Instructions | `SKILL.md` の本文                                   | Agent が関係あると判断して `read_file` を呼んだとき        | LLM が判断し、ファイルシステムツールで読む   |
| Level 3: Resources    | `scripts/`、`references/`、`assets/` 配下のファイル | 指示の中でファイルが参照されたとき                         | LLM が自分で判断して読む                     |

処理の流れ：

- **起動段階**：`SkillsMiddleware` が設定されたディレクトリ配下の Skill サブディレクトリを走査し、各 `SKILL.md` の frontmatter から `name` と `description` を取り出してシステムプロンプトに入れる

- **読み込み段階**：`SkillsMiddleware` は使える Skills の一覧と読み方の案内を渡す。ユーザーがリクエストを送ると、Agent は `description` をもとにどの Skill が必要かを判断し、`read_file` で対応する `SKILL.md` を読んで本文をコンテキストに入れる。

- **実行段階**：Agent は本文の指示に従って作業する。指示が `references/` や `assets/` 配下のファイルを参照していれば、読むかどうかは Agent が自分で決める。この段階は LLM が制御し、ミドルウェアはもう関与しない。

#### 複数ソースの Skills と優先順位

Skills は `create_deep_agent` の `skills` 引数でパスを渡せる

```python
agent = create_deep_agent(
    model=model,
    backend=backend,
    skills=[path1,...],
)
```

複数のパスに同じ名前の Skill があると、後ろのものが前のものを上書きする

プロジェクトのルールをチームのルールより優先したい場合

```
skills/
├── team/                           ← チーム共有版（優先度低）
│   ├── report-format/SKILL.md      ← チーム版のレポート形式
│   └── citation-style/SKILL.md     ← チーム版の引用形式
└── project/                        ← このプロジェクト版（優先度高）
    └── report-format/SKILL.md      ← プロジェクト版のレポート形式
```

渡すときは次のようにできる

```python
agent = create_deep_agent(
    model=model,
    backend=backend,
    skills=["/skills/team/", "/skills/project/"],
)
```
こうすると、レポートを書くときはプロジェクトのレポート形式が自動で使われ、引用はチームの形式に従う

実行結果

```
== skills=['/skills/team/', '/skills/project/']
   **Team Skills**: `/skills/team/`
   **Project Skills**: `/skills/project/` (higher priority)
   - **citation-style**: レポートで出典を引用するときに使う。チームで統一した引用番号の形式を提供する。
   -> Read `/skills/team/citation-style/SKILL.md` for full instructions
   - **report-format**: AI ニュースの日報を書くときに使う。このプロジェクトのレポート構成を提供する（……）。
   -> Read `/skills/project/report-format/SKILL.md` for full instructions
```

典型的な階層化の方針：

| 階層               | パス               | 内容                                     |
| ------------------ | ------------------ | ---------------------------------------- |
| 組織レベル         | `/skills/org/`     | 会社の規範、セキュリティレビュー         |
| チームレベル       | `/skills/team/`    | チームのワークフロー、Code Review の基準 |
| プロジェクトレベル | `/skills/project/` | プロジェクト固有のデプロイ手順、テスト方針 |



#### 使い方

Deep Agents には Skills を読み込むための Backend が 3 つあり、それぞれファイルの保存方法が異なる。

**基本的な使い方（FilesystemBackend）**

ローカルディスクから Skills のファイルを直接読む。ローカル開発や CLI の場面に向いている

```python
from deepagents import create_deep_agent
from deepagents.backends.filesystem import FilesystemBackend

backend = FilesystemBackend(root_dir="./my-project", virtual_mode=True)

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    backend=backend,
    # Skill サブディレクトリの親ディレクトリ。複数指定できる
    # パスはスラッシュ / で区切る
    skills=["/skills/"],
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is LangGraph?"}]},
    config={"configurable": {"thread_id": "1"}},
)
```

**StateBackend：state 経由で Skills を注入する**

StateBackend はファイルを LangGraph の agent state に保存する。ディスクのない環境（serverless でのデプロイなど）や、Skill の内容を動的に注入したい場面に向いている
仮想パスは / で始める必要がある（絶対パス形式）


```python
from urllib.request import urlopen
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.backends.utils import create_file_data
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
backend = StateBackend()

# リモートから Skill を読み込む（ローカルから読んでもよい）
skill_url = "https://raw.githubusercontent.com/langchain-ai/deepagents/refs/heads/main/libs/code/examples/skills/langgraph-docs/SKILL.md"
with urlopen(skill_url) as response:
    skill_content = response.read().decode('utf-8')

# 内容は create_file_data() で整形する必要がある
skills_files = {
    "/skills/langgraph-docs/SKILL.md": create_file_data(skill_content),
}

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    backend=backend,
    skills=["/skills/"],
    checkpointer=checkpointer,
)

result = agent.invoke(
    {
        "messages": [{"role": "user", "content": "What is langgraph?"}],
        # files 引数で注入する。呼び出しのたびに渡す必要がある
        "files": skills_files,  
    },
    config={"configurable": {"thread_id": "12345"}},
)
```

**StoreBackend：スレッドをまたいだ永続化**

StoreBackend は LangGraph の Store で永続化する。ファイルは一度書き込めば、すべてのスレッドからアクセスできる。つまり Skill は一度書けば、すべてのセッションで読める。

```python
from urllib.request import urlopen
from deepagents import create_deep_agent
from deepagents.backends import StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
# namespace 引数は関数。runtime config を受け取り、名前空間のタプルを返す
backend = StoreBackend(namespace=lambda _rt: ("filesystem",))

skill_url = "https://raw.githubusercontent.com/langchain-ai/deepagents/refs/heads/main/libs/code/examples/skills/langgraph-docs/SKILL.md"
with urlopen(skill_url) as response:
    skill_content = response.read().decode('utf-8')

# ここでファイルを注入するので、invoke のたびに渡す必要はない
store.put(
    namespace=("filesystem",),
    key="/skills/langgraph-docs/SKILL.md",
    value=create_file_data(skill_content),
)

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    backend=backend,
    store=store,
    skills=["/skills/"],
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is langgraph?"}]},
    config={"configurable": {"thread_id": "12345"}},
)
```

`namespace` について：
- `namespace` は Store の中の「引き出し」で、あるデータを誰と共有し、誰と分離するかを決める
- `namespace` は階層になっているので、タプルを使う
- Store のデータにはそれぞれ `(namespace, key)` という 2 段階のアドレスがあり、どの引き出しのどのファイルかを表す（ファイルパスからはルーティングのプレフィックス `/memories/` を除く）
- ここで `namespace` を関数にしているのは、引数によって別の `namespace` に振り分けられるからだ
  ```python
  # user_id が違えば別の namespace になる
  # rt は runtime の略
  # rt.context.user_id は
  # agent = create_deep_agent(...,context_schema=TenantContext) で構造を宣言し
  # invoke(..., context=UserContext(user_id=...)) のたびに渡す
  # UserContext は自分で定義した dataclass
  lambda rt: ("users", rt.context.user_id)
  ```
  これは次と同じ
  ```python
  def pick_namespace(rt):
    return ("users", rt.context.user_id)
  ```
- 詳しくは第 8 章で扱う

**実行時の動的な読み込み**

ユーザーのロール、テナント、リクエストの種類によって、読み込む Skill の組み合わせを変えられる
- ユーザーのロールで分ける：エンジニアにはコード関連の Skills、データチームには分析の Skills を見せる
- テナントの設定で分ける：SaaS では顧客ごとに別の Skill パッケージを有効にする
- リクエストのコンテキストで分ける：ユーザー入力の意図から関連する Skills を事前に絞り込む
- 環境変数で分ける：開発環境ではデバッグ用の Skills、本番環境では運用の Skills を読み込む

```python
from deepagents import create_deep_agent

SKILLS_BY_ROLE = {
    "engineering": ["/skills/code-review/", "/skills/testing/", "/skills/deployment/"],
    "data": ["/skills/sql-analysis/", "/skills/visualization/", "/skills/data-pipeline/"],
    "support": ["/skills/ticket-triage/", "/skills/runbook/"],
}

def create_agent_for_user(user_role: str):
    return create_deep_agent(
        model="anthropic:claude-sonnet-4-6",
        skills=SKILLS_BY_ROLE.get(user_role, []),
    )
```

#### Skill の権限管理

本番環境では、Skill の権限管理で 3 つの観点に注意する：

- 可視性（Visibility）：Agent がその Skill を見つけて読めるか
- 書き込み権限（Write Access）：Agent が Skill ファイルの内容を変更できるか
- 承認フロー（Approval）：書き込みに人の確認が必要か

**読み取り専用の Skills（社内ナレッジベースの場面）**

`FilesystemPermission` と `CompositeBackend` を組み合わせて、`skills` フォルダへの `write` 権限を禁止する

```python
from dataclasses import dataclass

from deepagents import FilesystemPermission, create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.store.memory import InMemoryStore

# テナントごとの組織番号を保存する
@dataclass(frozen=True)
class TenantContext:
    org_id: str

def org_skill_namespace(rt):
    # rt.context.org_id を読む
    # org_id がなければ "default-org" を返す
    org_id = getattr(rt.context, "org_id", "default-org")
    return ("curated-skills", org_id)

store = InMemoryStore()
store.put(
    # この skill は "org-acme" 専用
    namespace=("curated-skills", "org-acme"),
    # /skills/ は CompositeBackend のマウント用プレフィックス。Store の中ではルーティングからの相対パスを使う。
    key="/test-skill/SKILL.md",
    value=create_file_data("""---
name: test-skill
description: 読み取り専用の Skill が見つかり、読み込めることを確認するために使う。
---

# test-skill
"""),
)

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    # context の構造を定義する
    context_schema=TenantContext,
    backend=CompositeBackend(
        default=StateBackend(),
        # "/skills/" を操作するときは名前空間を切り替える
        routes={
            "/skills/": StoreBackend(
                namespace=org_skill_namespace,
            ),
        },
    ),
    skills=["/skills/"],
    permissions=[
        FilesystemPermission(
            # write_file、edit_file、delete はすべて拒否される
            operations=["write"],
            paths=["/skills/**"],
            mode="deny",
        ),
    ],
    store=store,
)

agent.invoke(
    {"messages": [{"role": "user", "content": "使える Skills を一覧表示して"}]},
    # 呼び出し時に context を渡す
    context=TenantContext(org_id="org-acme"),
    config={"configurable": {"thread_id": "1"}},
)
```

**書き込みには承認が必要（interrupt モード）**

Agent に変更を提案させるが、反映するには人の承認が必要

```python
from deepagents import FilesystemPermission, create_deep_agent
from langgraph.checkpoint.memory import MemorySaver

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    skills=["/skills/personal/"],
    permissions=[
        FilesystemPermission(
            operations=["write"],
            paths=["/skills/**"],
            mode="interrupt",
        ),
    ],
    checkpointer=MemorySaver(),  # interrupt には checkpointer が必要
)
```
- `interrupt` モードは一時停止したときの状態を checkpointer に保存するので、`MemorySaver` などの永続化できる checkpointer を必ず設定する
- この機能には `deepagents>=0.6.8` が必要
- LangGraph Studio では `interrupt` が自動で承認 UI として表示される。API から呼び出す場合は、クライアントが状態をポーリングして承認結果を送る必要がある

**共有 + 個人の Skills の階層化**

実際の運用で最もよく使われるのは 2 層構成で、チームで共有する読み取り専用の Skill ライブラリと、ユーザーごとの書き込み可能な Skill 領域を組み合わせる

```python
from dataclasses import dataclass
from langchain_openai import ChatOpenAI
from deepagents import FilesystemPermission, create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore
# 自分で書いたファイル。.env のキーや各種設定を渡すために使う
import config

@dataclass(frozen=True)
class TenantContext:
    org_id: str
    user_id: str

def shared_skill_namespace(rt):
    org_id = getattr(rt.context, "org_id", "default-org")
    return ("curated-skills", org_id)

def personal_skill_namespace(rt):
    if rt.server_info and rt.server_info.user:
        return ("user-skills", rt.server_info.user.identity)
    user_id = getattr(rt.context, "user_id", "local-user")
    return ("user-skills", user_id)

store = InMemoryStore()

# 共有 skills と個人 skills を読み込む
store.put(
    # org-acme 専用
    namespace=("curated-skills", "org-acme"),
    key="/team-report/SKILL.md",
    value=create_file_data("---\nname: team-report\ndescription: チームで共有する日報の形式\n---\n\n# team-report\n")
)
store.put(
    # alice 専用
    namespace=("user-skills", "alice"),
    key="/my-notes/SKILL.md",
    value=create_file_data("---\nname: my-notes\ndescription: alice 個人のノートの形式\n---\n\n# my-notes\n")
)

model = ChatOpenAI(
    model=config.MODEL_NAME, 
    api_key=config.DEEPSEEK_API_KEY, 
    base_url=config.BASE_URL,
)

agent = create_deep_agent(
    model=model,
    context_schema=TenantContext,
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/skills/shared/": StoreBackend(
                namespace=shared_skill_namespace,
            ),
            "/skills/personal/": StoreBackend(
                namespace=personal_skill_namespace,
            ),
        },
    ),
    skills=["/skills/shared/", "/skills/personal/"],
    permissions=[
        FilesystemPermission(
            operations=["write"],
            paths=["/skills/shared/**"],
            mode="deny",
        ),
    ],
    store=store,
    checkpointer=InMemorySaver(),
)

# スレッド番号。get_state はこれで今回の実行で保存した状態を探す
config = {"configurable": {"thread_id": "t1"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "使える Skills を一覧表示して"}]},
    context=TenantContext(org_id="org-acme", user_id="alice"),
    config=config
)
print(result["messages"][-1].content)

# スレッド t1 の状態をすべて読む。invoke の戻り値にない skills_metadata も含む
values = agent.get_state(config).values
for s in values.get("skills_metadata") or []:
    print(s["name"], "|", s["path"], "|", s["description"])
print("読み込みエラー:", values.get("skills_load_errors"))
```

実行結果

```json
現在使える Skills は **2 個**です：

| Skill         | 出所                             | 説明                       | パス                                  |
| ------------- | -------------------------------- | -------------------------- | ------------------------------------- |
| `team-report` | 共有（Shared）                   | チームで共有する日報の形式 | `/skills/shared/team-report/SKILL.md` |
| `my-notes`    | 個人（Personal、優先度が高い）   | alice 個人のノートの形式   | `/skills/personal/my-notes/SKILL.md`  |

補足：

- **優先度**：個人の Skills（`/skills/personal/`）は共有の Skills（`/skills/shared/`）より優先されます。両方が同じことを扱う場合は個人の Skill に従い、タスクが個人の Skill と関係ない場合にだけ共有の Skill を使います。
- **実際の内容**：どちらの `SKILL.md` にも、今は YAML frontmatter（`name` と `description`）と見出しが 1 行あるだけで、**具体的な形式の説明はまだ書かれていません**。ディレクトリには補助スクリプトや参考ファイルもありません。
- **影響**：そのため今のところ「登録名」にすぎず、実行できる手順やテンプレートはありません。これに従って日報やノートを作っても自己流になり、チームの形式どおりになる保証はありません。

実際に使えるようにしたい場合は、日報の項目、ノートの見出し階層やメタ情報の要件など、具体的なテンプレートや規範をこの 2 つのファイルに加えてください。私が書くこともできます。
team-report | /skills/shared/team-report/SKILL.md | チームで共有する日報の形式
my-notes | /skills/personal/my-notes/SKILL.md | alice 個人のノートの形式
読み込みエラー: []
```

#### Skills でコードを実行する

**サンドボックスのスクリプト（Sandbox Scripts）**

Skill のファイルがサンドボックスの外に保存されている場合（StateBackend を使う場合など）は、カスタムミドルウェアで Agent の実行前後にファイルを同期する必要がある：

- `before_agent`：Skill のスクリプトをサンドボックス環境にアップロードする
- `after_agent`：サンドボックスの出力ファイルをダウンロードして戻す

このパターンは、データ処理、API 呼び出し、ファイル変換などを実行する場面に向いていて、実行を安全に隔離できる

**インタープリタ Skills（Interpreter Skills）**

インタープリタ Skills は、Skill 内のコードモジュールを Agent のコードインタープリタ環境に公開する
Agent はテスト済みの補助関数を直接 import でき、毎回ロジックを生成し直す必要がない
ただし、事前に QuickJS ミドルウェアをインストールしておく必要がある

Skill を import できるようにするには、3 つの設定が必要：

- frontmatter の `metadata.entrypoint` で入口ファイル（JS/TS）を指定する
- `CodeInterpreterMiddleware` に同じバックエンドを使わせる
- Agent はコードの中で `await import("@/skills/<name>")` で import する

[サンプルコード](https://datawhalechina.github.io/deepagents-in-action/chapters/ch07-skills/#%E8%A7%A3%E9%87%8A%E5%99%A8%E6%8A%80%E8%83%BDinterpreter-skills)

#### Skills、Memory、Tools の比較


|                    | Skills                                              | Memory（`AGENTS.md`）                    | Tools                                                                  |
| ------------------ | --------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------- |
| 用途               | 必要に応じて読み込むドメインの能力（段階的な開示）  | 起動時に読み込む永続的なコンテキスト     | Agent が呼び出せるプログラム上の操作                                   |
| 読み込むタイミング | Agent が関係あると判断したときだけ読む              | Agent の起動時に読み込む                 | 毎ターン使える                                                         |
| 形式               | 名前付きディレクトリ内の `SKILL.md`                 | `AGENTS.md` ファイル                     | Agent にバインドした関数                                               |
| 優先順位           | 後のものが上書き（last wins）                       | ユーザーレベル + プロジェクトレベルをマージ | 作成時に定義                                                        |
| 向いている場面     | タスク専用で、大きくなりうる指示セット              | 常に関係するグローバルな規範や好み       | Agent が操作を実行する必要がある場合、またはファイルシステムがない場合 |

#### Skills のベストプラクティス

- `description` は簡潔に保つ。`{具体的な使用場面}のときに使う。{機能の一言説明}`
- `SKILL.md` の本文は 5000 tokens / 500 行以内に収め、詳しく書く必要がある内容は `references/` に置いて必要なときに読み込む
- 人間ではなく Agent 向けに構成する
  - 手順化：段落で説明するのではなく、1-2-3 のように手順を明確にする
  - 判断基準：分岐でどう選ぶか（if X then A, else B）
  - 入力/出力の例（できるだけ一般化した例にすべきだと思う）
  - 境界ケースの扱い：よくある例外にどう対応するか
- Skill の数を管理する

#### 所感

Skill にアクセス権限を付けるという考え方には初めて触れた。実際のエンジニアリングでは、Skill パッケージ同士を分けておくと、後のメンテナンスがしやすく、影響も最小限に抑えられる。

## 実践: AI ニュースアシスタントの重複チェックと過去ニュースの照合を Skills に移す

Task4 で分けた 4 つのサブ Agent のうち、news-categorizer と old-news-checker の判断基準は system_prompt に数文で書かれているだけだった。第 7 章を学んだあと、重複チェックと過去ニュース照合のルールを 2 つの Skill にまとめてそれぞれのサブ Agent に渡し、system_prompt には役割と入出力だけを残した。

リポジトリ: [ryukirin/ai-news-deep-agent](https://github.com/ryukirin/ai-news-deep-agent)

### Skill のディレクトリと割り当て

```text
skills/
├── news-categorizer/
│   └── news-dedup/
│       └── SKILL.md      ← news-categorizer が読み込む
└── old-news-checker/
    └── history-check/
        └── SKILL.md      ← old-news-checker が読み込む
```

| サブ Agent       | Skill           | 定めている内容                                                                   |
| ---------------- | --------------- | -------------------------------------------------------------------------------- |
| news-categorizer | `news-dedup`    | 現在のリスト内での重複チェックの手順、何を重複とみなすかの例、境界ケース         |
| old-news-checker | `history-check` | `/history/news_history.txt` との照合手順、履歴の書き込み形式、例、境界ケース     |

- サブ Agent はメイン Agent の skills を継承しないので、2 つのサブ Agent の定義でそれぞれ `skills` に読み込み元のディレクトリを指定した。読み込み元はサブ Agent 名ごとに分けてあり、news-categorizer は `news-dedup` だけ、old-news-checker は `history-check` だけを読み込む
- `/skills/` はプロジェクトの `skills/` ディレクトリ（`FilesystemBackend`）にルーティングし、`FilesystemPermission` で `/skills/**` への書き込みを拒否した。サブ Agent は自分の `permissions` を設定していないのでこのルールを継承し、Skill はどの Agent からも読み取り専用になる

### `SKILL.md`

`news-dedup`：

```markdown
---
name: news-dedup
description: 現在のニュース記事リストに重複したニュースがないか確認するときに使う。重複したニュースを現在のニュース記事リストから取り除く。
---

# news-dedup

## 手順

1. 現在のニュース記事リストを比較し、重複または類似したニュース内容がないか確認する。
2. 現在のニュース記事リストに重複したニュース内容があれば、重複のうち質の低いニュースをリストから削除する。
3. 重複のない構造化したニュース記事のリストを返す。

## 例
ニュース1：A 社が新製品 X を発表し、来月発売の予定。
ニュース2：A 社の X は来月発売の予定。その特徴と機能も紹介されている。
この 2 つのニュースは同じニュースに属するので、重複とみなす。質の低いほうを削除する原則に従い、ニュース2 のほうが内容が豊富なので、ニュース2 を残してニュース1 を削除する。

ニュース3：A 社の X。その市場での位置づけと販売戦略も詳しく紹介されている。
このニュースはニュース1・ニュース2 と内容が似ているが焦点が異なるため、重複とはみなさない。

ニュース4：A 社の新製品 X の特徴と機能。
このニュースはニュース1・ニュース2 と比較する必要がある。内容の類似度が高く、焦点も同じであれば、重複とみなす。質が同程度であれば、ランダムに 1 件を残せばよい。

## 境界ケース

- 現在のニュース記事リストが空なら、空のリストを返す。
- 現在のニュース記事リストのすべてのニュースが互いに重複していれば、ニュース記事を 1 件だけ返す。
- 現在のニュース記事リストにニュースが 1 件しかなければ、そのまま返す。
```

`history-check`：

```markdown
---
name: history-check
description: 現在のニュース記事リストに /history/news_history.txt の過去のニュースが含まれていないか確認するときに使う。過去のニュースを現在のニュース記事リストから取り除く。
---

# history-check

## 手順

1. /history/news_history.txt ファイルから過去のニュースのリストを読み込む。
2. 現在のニュース記事リストの記事を過去のニュースのリストと比較し、重複または類似したニュース内容がないか確認する。
3. 現在のニュース記事リストの記事が過去のニュースのリストのいずれかと内容が重複していれば、その記事をリストから削除する。
4. すべての確認が終わったら、現在のニュース記事リストのうち重複していない記事を /history/news_history.txt ファイルに追記し、過去のニュースのリストが欠けないようにする。
5. 過去のニュースを含まない構造化したニュース記事のリストを返す。

## news_history.txt の書き込み形式
1 行に 1 件のニュースで、形式は次のとおり：
日付 | タイトル | 要約

## 例
過去のニュース：A 社が新製品 X を発表し、来月発売の予定。
ニュース1：A 社の X は来月発売の予定。
ニュース2：A 社の X。
この 3 つのニュースはいずれも同じニュースに属するので、重複とみなす。

ニュース4：A 社の新製品 X の特徴と機能。
このニュースは過去のニュースと比較する必要がある。内容の類似度が高く、焦点も同じであれば、重複とみなす。

## 境界ケース

- 現在のニュース記事リストが空なら、空のリストを返す。
- /history/news_history.txt ファイルが存在しないか空であれば、そのファイルを新しく作って現在のニュース記事リストを追記し、現在のニュース記事リストを返す。
- 現在のニュース記事リストのすべてのニュースが過去のニュースのリストと重複していれば、空のリストを返す。
```
