## ノート

### 第 4 章 タスクの計画と分解：Agent に複雑なタスクを分解させる

#### todo の 3 つの状態

| 状態        | 意味   | 典型的な場面                           |
| ----------- | ------ | -------------------------------------- |
| pending     | 未着手 | Agent が計画したばかりで、まだ始めていない |
| in_progress | 進行中 | Agent がこのステップを実行している     |
| completed   | 完了   | Agent がタスクを完了にした             |

Agent が todo を更新する例：

`write_todos` の呼び出し
```
Updated todo list to [{'content': '2026-10-17 前後の最新 AI ニュースを収集（複数ソースで検索）', 'status': 'in_progress'}, {'content': '検索結果の重複を除去し、候補ニュースのリストを作る', 'status': 'pending'}, {'content': '/history/news_history.txt と照合し、報道済みのニュースを除外', 'status': 'pending'}, {'content': '新しいニュースのタイトル + 要約を history/news_history.txt に追記', 'status': 'pending'}, {'content': 'レポートを書き、report/2026-10-17.md として保存', 'status': 'pending'}]
```

#### todo リストの永続化

タスクリストは Agent State の todos フィールドに保存される

```json
{
    "todos":[
        {
            "content":"2026-10-17 前後の最新 AI ニュースを収集（複数ソースで検索）",
            "status":"in_progress"
        },
        {
            "content":"検索結果の重複を除去し、候補ニュースのリストを作る",
            "status":"pending"
        },
        {
            "content":"/history/news_history.txt と照合し、報道済みのニュースを除外",
            "status":"pending"
        },
        {
            "content":"新しいニュースのタイトル + 要約を history/news_history.txt に追記",
            "status":"pending"
        },
        {
            "content":"レポートを書き、report/2026-10-17.md として保存",
            "status":"pending"
        }
    ]
}
```

- 複数回の `invoke()` の間でリストを自動で引き継ぐには、Checkpointer を設定し、同じ `thread_id` を使い回す必要がある。`TodoListMiddleware` を追加するだけでは、前回の実行の状態は引き継がれない
- `InMemorySaver` は現在のプロセスの中だけにチェックポイントを保存する。プロセスの再起動後も復元するには、データベースなどの永続的な Checkpointer を使う必要がある。Agent Server にデプロイした場合は、プラットフォームが永続化の機能を提供する
- `subagents=[...]` で宣言したサブ Agent は独自の Middleware スタックを持つ。計画機能が必要な場合は、自分の spec で Todo を有効にしなければならない。また、メイン Agent のリストは読まない

#### LangChain のミドルウェア

`create_deep_agent()` が内部で行っていることは、本質的には一連のミドルウェアを Agent に自動で組み込むことである

**2 種類の Hook**

| スタイル   | Hook                                                         | 実行のされ方                                                                                 | 向いている場面                                 |
| ---------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Node-style | `before_agent`、`before_model`、`after_model`、`after_agent` | Agent グラフの独立したノードにコンパイルされ、ライフサイクルの順に実行される                 | 検証、状態の更新、監査、人による中断           |
| Wrap-style | `wrap_model_call`、`wrap_tool_call`                          | 1 回のモデルまたはツールの呼び出しを包む。`handler` は呼ばなくても、1 回でも複数回でもよい | リトライ、キャッシュ、フォールバック、リクエストやレスポンスの変換 |

Node-style にはグラフのノードという明確な境界があるため、人による中断 `interrupt()` を設定するのに向いている

**デフォルトのミドルウェア**

- `FilesystemMiddleware`：7 つのファイルツールを注入し、permissions の権限ルールを適用する
- `SummarizationMiddleware`：コンテキストを自動で圧縮する。発動のしきい値は設定できる
- `PatchToolCallsMiddleware`：メッセージ履歴に欠けているツールの応答を補う
- Prompt caching などモデル関連の機能：有効になるかどうかはモデルと Harness profile による

**パラメータで設定するミドルウェア**

- `SubAgentMiddleware`：`subagents=` で設定する。デフォルトで general-purpose サブ Agent を含み、task ツールを提供する
- `SkillsMiddleware`：`skills=` を渡すと有効になり、スキルパッケージを注入する
- `AsyncSubAgentMiddleware`：非同期のサブ Agent を渡すと有効になる
- `MemoryMiddleware`：`memory=` を渡すと有効になり、AGENTS.md の記憶を注入する
- `HumanInTheLoopMiddleware`：`interrupt_on=` を渡すと有効になり、指定したツール呼び出しを止めて人の承認を待つ

**`middleware=[...]` で設定するミドルウェア**

- `TodoListMiddleware` などのオプションの方針は、必要に応じて追加できる
- デフォルトの Middleware と同じ名前のインスタンスは、元の位置でデフォルトのインスタンスを置き換える。末尾にもう 1 つ追加されることはない
- 元の位置での置き換えはインスタンス全体の差し替えで、新旧の設定をフィールドごとにマージすることはない


| 分類         | ミドルウェア             | 用途                                                       |
| ------------ | ------------------------ | ---------------------------------------------------------- |
| 計画         | TodoListMiddleware       | タスクの計画と追跡。write_todos と todos 状態を注入する    |
| 安全         | PIIMiddleware            | 個人情報の検出とマスキング                                 |
| 耐障害性     | ToolRetryMiddleware      | ツール呼び出しが失敗したときに自動でリトライする           |
| 耐障害性     | ModelRetryMiddleware     | モデル呼び出しが失敗したときに自動でリトライする           |
| 耐障害性     | ModelFallbackMiddleware  | メインのモデルが失敗したときに予備のモデルへ自動で切り替える |
| 制限         | ToolCallLimitMiddleware  | ツールの呼び出し回数を制限する                             |
| 制限         | ModelCallLimitMiddleware | モデルの呼び出し回数を制限する                             |
| コンテキスト | ContextEditingMiddleware | 古いツール呼び出しの結果を整理する                         |

#### PatchToolCallsMiddleware（Node-style）

履歴にツール呼び出しのリクエストだけがあり、ツールの応答メッセージがない状態（実行のキャンセルや引数の破損など）で次の実行をすると、`PatchToolCallsMiddleware` が `before_agent` Hook で履歴を確認し、欠けている応答の代わりに `ToolMessage` を 1 件補って、その呼び出しがキャンセルされたことを伝える。引数が壊れていたり途中で切れていたりした呼び出しについては、実行できなかったことを伝える。

```python
from langchain_core.messages import AIMessage
from langgraph.checkpoint.memory import InMemorySaver

# deepagents-in-action コースのプロジェクトにあるテスト用モデル。responses に用意した返答を順に返す
from course_notebooks.testing import ScriptedChatModel
from deepagents import create_deep_agent

executed = []  # echo が実際に実行されたかを記録する


def echo(text: str) -> str:
    """Return the text unchanged."""
    executed.append(text)
    return f"echo: {text}"


model = ScriptedChatModel(responses=[
    AIMessage(content="", tool_calls=[{"name": "echo", "args": {"text": "hello"}, "id": "call_1"}]),
    AIMessage(content="2 回目の実行の返答"),
])
agent = create_deep_agent(model=model, tools=[echo], checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "demo"}}


def show(title):
    """
    チェックポイントに保存されたメッセージを出力する
    args:
        title: 今回の出力の見出し
    return:
        None
    """
    print(f"\n== {title}")
    for m in agent.get_state(config).values["messages"]:
        calls = [c["id"] for c in getattr(m, "tool_calls", [])]
        extra = f" tool_calls={calls}" if calls else ""
        extra += f" tool_call_id={m.tool_call_id} status={m.status}" if m.type == "tool" else ""
        print(f"  {m.type:<6}{extra}  {str(m.content)[:60]!r}")


# 1 回目の実行：model ノードが終わったらすぐに止め、ユーザーによるキャンセル、プロセスのクラッシュ、タイムアウトなどを再現する
for update in agent.stream({"messages": [{"role": "user", "content": "echo hello"}]}, config, stream_mode="updates"):
    print("完了したノード:", list(update))
    if "model" in update:
        break

show("1 回目の実行がキャンセルされた後のチェックポイント内のメッセージ")
print("  echo の実行回数:", len(executed))

# 2 回目の実行：同じ thread_id で、before_agent が先に履歴を確認し、欠けているツールの応答を補う
agent.invoke({"messages": [{"role": "user", "content": "続けて"}]}, config)
show("2 回目の実行後のチェックポイント内のメッセージ")
print("  echo の実行回数:", len(executed))
------------------------------------------
完了したノード: ['PatchToolCallsMiddleware.before_agent']
完了したノード: ['model']

== 1 回目の実行がキャンセルされた後のチェックポイント内のメッセージ
  human   'echo hello'
  ai     tool_calls=['call_1']  ''
  echo の実行回数: 0

== 2 回目の実行後のチェックポイント内のメッセージ
  human   'echo hello'
  ai     tool_calls=['call_1']  ''
  tool   tool_call_id=call_1 status=error  'Tool call echo with id call_1 did not complete - no result w'
  human   '続けて'
  ai      '2 回目の実行の返答'
  echo の実行回数: 0
```

`tool   tool_call_id=call_1 status=error  'Tool call echo with id call_1 did not complete - no result w'` が補われた `ToolMessage` である

実行中のさまざまな異常への対処は次のとおり。


| どんな状況か                                   | 誰が対処するか                                  | 注意すること                                                                       |
| ---------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------- |
| 履歴にツール呼び出しがあるのに、対応する応答がない | `PatchToolCallsMiddleware` が説明のメッセージを補う | ツールをリトライせず、結果が正しいかどうかも検証しない                             |
| ツール呼び出しでリトライ可能な例外が起きた     | アプリが明示的に設定した `ToolRetryMiddleware`  | リトライするか、何回リトライするかは方針で決まる。書き込み操作では重複実行も考慮する |
| 次の実行で前回の状態から続ける                 | Checkpointer と同じ `thread_id`                 | プロセスをまたいで復元するには、永続的な Checkpointer が必要                       |
| ツールが内容を返したが、その内容が正しいか     | アプリの検証、評価、または人によるレビュー      | 呼び出しの成功やリストの完了は、結果が正しいことを意味しない                       |

#### TodoListMiddleware（両方のスタイルを使う）

- `wrap_model_call`：モデルを呼び出すたびに、計画用のプロンプトをそのリクエストに加える
- `after_model`：モデルの返答の後、同じ返答の中で `write_todos` が複数回並列に呼ばれていないかを確認し、呼ばれていればエラーを返す


`write_todos` の実体は LangChain の `TodoListMiddleware` である。これを追加すると、Agent は次のものを自動で得る。

- `write_todos` ツール：タスクリストを作成・管理する
- `todos` 状態：タスクとその状態を保存し、後のステップや UI で使う。呼び出しをまたいだ引き継ぎは Checkpointer が担当する
- 計画ガイドのプロンプト：複雑なタスクでは、先に計画してから実行するよう Agent を導く

**カスタム設定**

`TodoListMiddleware` には次の 2 つのパラメータを設定できる
```python
TodoListMiddleware(
    system_prompt="...",      # 計画ガイドのプロンプトをカスタマイズ
    tool_description="...",   # write_todos ツールの説明をカスタマイズ
)
```

#### SummarizationMiddleware（Wrap-style）

コンテキストの圧縮を担当する。

パスを指定して履歴を読み戻す場合は、同じ Backend を使う `FilesystemMiddleware` も設定する必要がある。`compact_conversation` ツール（手動の圧縮）を提供するのは別の `SummarizationToolMiddleware` で、ここでの自動要約とは別に設定する。

要約のしきい値は自動で設定されるが、自分で上書きすることもできる。

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.middleware.summarization import SummarizationMiddleware

# FilesystemBackend など自分でデータを保存する backend に替える場合は、この 1 つのオブジェクトを使うすべての場所に渡す
backend = StateBackend()

agent = create_deep_agent(
    model=model,
    # FilesystemMiddleware は自分で設定しなくてよい。create_deep_agent がこの backend で自動的に組み込む
    backend=backend,
    middleware=[
        # デフォルトの要約ミドルウェアと同じ名前なので、その場で置き換わる。trigger を設定しないと自動要約は行われない
        SummarizationMiddleware(
            model=model,
            backend=backend,
            trigger=("tokens", 100000),
            keep=("messages", 6)
        ),
    ],
)
```

**LangChain 版との比較**

LangChain では Node-style で、`before_model` / `abefore_model` で実行される。現在の `state["messages"]` にある古いメッセージを要約に置き換え、最近のメッセージを残す。
Deep Agents では Wrap-style で、モデルを呼び出すときに実行される。元のメッセージは残し、要約と切り詰めの位置を別に記録したうえで、要約対象の古いメッセージを Backend に書き込み、要約に保存先のパスを付ける。

### 所感

この章では主に各ミドルウェアとその実装を扱い、特にタスク計画とコンテキストの要約に重点が置かれていた。
ミドルウェアはモデルにさまざまな能力を与えるものである。Deep Agents は一部のミドルウェアを自動で読み込み、ほかに自分で設定するミドルウェアもある。これらが Harness の要だと思う。
