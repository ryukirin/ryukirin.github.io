### 第 8 章 長期記憶：Agent に会話をまたぐ記憶を持たせる

#### Memory の仕組み

Agent は記憶をファイルとして読み書きし、それらのファイルをどこに保存するかは Backend で制御する

1. ストレージとファイルの準備：Backend と Store を設定し、読み込む記憶ファイルをあらかじめ用意する
2. 記憶の読み込み：
   1. `memory=` で**既存のファイル**のパスを指定し、内容はシステムプロンプトに入る
   2. `skills=` で Skill のサブディレクトリを含むディレクトリを指定し、まずメタデータを注入し、本文は Agent が必要に応じて読む
3. 記憶の更新（任意）：いつ、どのファイルに書き込むかをプロンプトで取り決め、Agent が `edit_file` などのツールを呼んで更新し、以降の会話で使う

#### Agent の 2 種類の「記憶」

**短期記憶：Thread-scoped**

デフォルトの StateBackend はファイルを LangGraph の Agent State に保存する。これは短期記憶の一種

- 同じ会話スレッド（thread）の中で永続化される
- 複数ターンの会話でも失われない（Checkpointer の仕組みによる）
- thread_id ごとに分離される
  - 新しいスレッドは古いスレッドの State にあるファイルを読めない
  - Checkpointer が古いスレッドの状態を保存している限り、古いスレッドに戻れば読める

[Checkpointer の詳細](#checkpointer-短期記憶の基礎)

**長期記憶：Cross-thread**

複数の会話の間で共有する必要がある情報を保存する

- ユーザーの好みの設定
- プロジェクトの背景知識
- 蓄積した調査結果
- Agent がフィードバックから学んだ改善指示

#### Checkpointer：短期記憶の基礎

チャットアプリにたとえるとわかりやすい：1 つのスレッドは 1 つのチャット画面、メッセージを 1 回送るのが 1 回の invoke、新しいチャットを作るのは新しい thread_id に切り替えること

```
スレッド thread_id="a1"            ← 1 つの会話（1 つのチャット画面）
├── 第 1 ターン invoke("私は張三です")   ← 1 回の実行
│     └── モデル → ツール → モデル …   ← 複数のステップ。各ステップの終了後に Checkpointer がスナップショットを 1 つ保存する
├── 第 2 ターン invoke("私の名前は？")
│     └── まず a1 の最新のスナップショットから State を復元し、続きを実行する
スレッド thread_id="a2"            ← 別の会話。自分の State を持ち、空の状態から始まる
```

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()

agent = create_deep_agent(
    model=model,
    checkpointer=checkpointer,
)

# 同じ thread_id の中では、Agent は前の会話を覚えている
config = {"configurable": {"thread_id": "conversation-001"}}
agent.invoke({"messages": [{"role": "user", "content": "私は張三です"}]}, config=config)
agent.invoke({"messages": [{"role": "user", "content": "私の名前は何ですか？"}]}, config=config)
# Agent は「あなたは張三です」と答えられる

# thread_id を変えると、Agent は覚えていない
config2 = {"configurable": {"thread_id": "conversation-002"}}
agent.invoke({"messages": [{"role": "user", "content": "私の名前は何ですか？"}]}, config=config2)
# Agent はあなたが誰か知らない
```

Checkpointer の仕組み：

- Agent が 1 ステップ実行するたびに、現在の状態（メッセージ履歴、ファイルシステムの状態、Todo を有効にした場合のタスクリストなど）を自動で保存する
- 次に呼び出したとき、thread_id が同じなら前回の状態を自動で復元する
- 開発では MemorySaver（メモリ上、再起動で消える）、本番では PostgresSaver（データベース、永続化）を使う

| 設定 | 結果 |
| --- | --- |
| Checkpointer を設定しない | invoke は毎回独立していて「スレッド」という概念がなく、ターンの間で何も保持しない |
| Checkpointer を設定したが thread_id を渡さない | そのままエラーになる：ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, ... |
| Checkpointer を設定し、thread_id も渡す | 同じ thread_id の複数ターンで 1 つの State を共有する |

**短期記憶の管理戦略**

| 戦略 | やり方 | 適した場面 |
| --- | --- | --- |
| Trim（切り詰め） | 直近 N 件のメッセージだけを残し、それより前は捨てる。カスタマイズしたい場合は `@before_model` ミドルウェアで行える | 単純で大まか。過去の文脈が要らない場面に向く |
| Delete（削除） | RemoveMessage で特定のメッセージを狙って削除する | 選択的に整理したい場合（機密情報の削除など） |
| Summarize（要約） | LLM で古いメッセージを要約に圧縮する。`SummarizationMiddleware` が自動で組み込まれていて、同名のもので上書きできる | 履歴の意味を残したい場合。最も推奨される方法 |

切り詰めロジックのカスタマイズ

```python
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langchain.agents import AgentState
from langchain.agents.middleware import before_model
from langgraph.runtime import Runtime

@before_model
def trim_messages(state: AgentState, runtime: Runtime) -> dict | None:
    """直近の数件のメッセージだけを残し、コンテキストのあふれを防ぐ。"""
    messages = state["messages"]
    if len(messages) <= 3:
        return None  # 切り詰めは不要

    first_msg = messages[0]  # 最初の 1 件を残す（通常はシステムメッセージ）
    recent = messages[-3:]   # 直近の 3 件を残す
    return {
        "messages": [
            RemoveMessage(id=REMOVE_ALL_MESSAGES),
            first_msg,
            *recent,
        ]
    }

# create_agent または create_deep_agent で middleware 引数に渡して追加する
agent = create_deep_agent(
    model=model,
    middleware=[trim_messages],
)
```

**発展：AgentState のカスタマイズ**

Deep Agents でデフォルトで使われるのは DeepAgentState、LangChain でデフォルトで使われるのは AgentState

|  | AgentState | DeepAgentState |
| --- | --- | --- |
| messages の保存方法 | add_messages：チェックポイントごとにその時点の完全なメッセージリストを 1 つ複製するので、過去のメッセージがどのチェックポイントにも重複して保存される | DeltaChannel：チェックポイントには完全なリストを入れず、各ステップで新しく追加された分だけを記録し、読み込むときに最初からその差分をつなぎ合わせる。約 50 ステップごとに完全なスナップショットを 1 回保存するので、読み込むたびに最初の 1 件からつなぐ必要はない |
| チェックポイントのサイズ | ステップ数の 2 乗で増える | ステップ数に比例して増える |
| 使われる場所 | create_agent の state_schema と、カスタムミドルウェアの state_schema | create_deep_agent の state_schema |

どちらもデフォルトで 3 つのフィールドを持つ
- `messages`：履歴メッセージ
- `jump_to`：ミドルウェアの内部で遷移を制御するためのフィールド。非公開で、外からは見えない
- `structured_response`：構造化出力

各ミドルウェアはデフォルトの State を継承して自分のフィールドを加えられる。Agent を作るとき、これらの構造が合わさって最終的な State になる

| ミドルウェア | 構造クラス | 追加するフィールド |
| --- | --- | --- |
| FilesystemMiddleware | `FilesystemState` | `files`（StateBackend のファイル） |
| TodoListMiddleware | `PlanningState` | `todos` |
| SkillsMiddleware | `SkillsState` | `skills_metadata` など |
| MemoryMiddleware | `MemoryState` | `memory_contents` |

フィールドに付けるアノテーションで、外から見えるかどうかが決まる：

- `OmitFromOutput`：invoke の戻り値に含まれない
- `PrivateStateAttr`：ミドルウェアの内部だけで使う

Checkpointer が各ステップで保存するのは、この State 全体

カスタマイズするときはデフォルトの State に新しいフィールドを追加し、同名の場合は上書きする

```python
# 主要なコードだけを残し、出力と write_todos の組み立ては省略
class MyState(DeepAgentState):
    """Deep Agents のデフォルトの State に新しいフィールドを 2 つ加え、同名のフィールドを 1 つ宣言し直す"""

    # 既存と名前が重ならない、マージのルールなし：更新時は新しい値で古い値を上書きする
    note: NotRequired[str]

    # 既存と名前が重ならない、operator.add：更新時に追加する
    tags: NotRequired[Annotated[list[str], operator.add]]

    # 同名（TodoListMiddleware にすでにある）、更新時に追加するよう変更する
    todos: NotRequired[Annotated[list, operator.add]]
```

ツールは ToolRuntime を通してこれらのカスタムの State のフィールドを読み書きできる

```python
@tool
def get_note(runtime: ToolRuntime) -> str:
    """現在のメモとタグを読み取る。"""

    # runtime.state で状態を読む
    return f"メモ：{runtime.state.get('note', '（なし）')}、タグ：{runtime.state.get('tags', [])}"

@tool
def update_note(new_note: str, runtime: ToolRuntime) -> Command:
    """メモを new_note に変更する。"""

    # Command(update={...}) で状態を書き込む
    return Command(update={
        "note": new_note,   # まるごと置き換える
        "messages": [ToolMessage(f"メモを {new_note} に変更しました", tool_call_id=runtime.tool_call_id)],
    })

@tool
def add_tag(tag: str, runtime: ToolRuntime) -> Command:
    """現在の会話にタグを 1 つ加える。"""

    # Command(update={...}) で状態を書き込む
    return Command(update={
        # operator.add は古いリストの後ろにつなげるので、新しく加える分だけを渡す
        "tags": [tag],
        "messages": [ToolMessage(f"タグ {tag} を追加しました", tool_call_id=runtime.tool_call_id)],
    })

agent = create_deep_agent(model=model, tools=[get_note, update_note, add_tag],
                          state_schema=MyState, checkpointer=InMemorySaver())
```

呼び出し時に初期値 `note="a"`、`tags=["x"]` を渡し、台本どおりに動くモデルが、読む、`note` を変更、`tag` を追加、もう一度読む、の順に実行する

#### CompositeBackend：長期記憶の中心となる仕組み

**実行時のアイデンティティと namespace**

`StoreBackend` は `namespace` で異なるユーザー、Agent、組織のデータを区別する
LangSmith / LangGraph Server にデプロイすると、`rt.server_info` で `assistant_id` とログインユーザーの情報を取得できる
ローカルで実行する場合やセルフホストの場合は、カスタムのフィールドを 1 つ追加する必要がある

```python
def assistant_namespace(rt):
    if rt.server_info:
        return (rt.server_info.assistant_id,)
    return ("local-agent",)


def user_namespace(rt):
    if rt.server_info and rt.server_info.user:
        return (rt.server_info.user.identity,)
    user_id = getattr(rt.context, "user_id", "local-user")
    return (user_id,)


def org_namespace(rt):
    org_id = getattr(rt.context, "org_id", "default-org")
    return (org_id,)
```

**Agent レベルの記憶（Agent-scoped）**

すべてのユーザーで共有し、1 つの Agent が 1 つの記憶を使う。上の `assistant_namespace()` を使う

```python
from deepagents import create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from dataclasses import dataclass

@dataclass(frozen=True)
class MemoryContext:
    user_id: str = "local-user"
    org_id: str = "default-org"

agent = create_deep_agent(
    model="google_genai:gemini-3.5-flash",
    context_schema=MemoryContext,
    memory=["/memories/AGENTS.md"],          # 起動時に自動で読み込む記憶ファイル
    skills=["/skills/"],
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/memories/": StoreBackend(
              # local-agent を例にすると、local-agent の memories の引き出しに保存する
                namespace=lambda rt: (*assistant_namespace(rt), "memories"),
            ),
            "/skills/": StoreBackend(
                namespace=lambda rt: (*assistant_namespace(rt), "skills"),
            ),
        },
    ),
)
```

**会話をまたいだアクセス**

```python
from dataclasses import dataclass
from uuid import uuid4

from deepagents import create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore


@dataclass
class UserContext:
    user_id: str


store = InMemoryStore()
# テストユーザー user-123
user = UserContext(user_id="user-123")
# user-123 の memories の中
namespace = (user.user_id, "memories")
# Agent がルーティングのプレフィックスを自動で付ける
key = "/preferences.md" 
# 具体的なファイル名
memory_path = "/memories/preferences.md"

# 先にファイルを作る。CompositeBackend は /memories/ のルーティングプレフィックスを取り除く
# これは新しい Store の初回の初期化
# 既存の Store では先にファイルを確認し、以前の好みを上書きしないようにする
if store.get(namespace, key) is None:
    store.put(namespace, key, create_file_data("# ユーザーの好み\nまだ記録はありません。"))

agent = create_deep_agent(
    model=model,
    context_schema=UserContext,
    store=store,
    checkpointer=InMemorySaver(),
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/memories/": StoreBackend(
                namespace=lambda rt: (rt.context.user_id, "memories"),
            ),
        },
    ),
    memory=[memory_path],
    system_prompt=(
        f"ユーザーが好みを覚えるよう明示的に求めたら、先に {memory_path} を読み、edit_file で更新する。"
        "ユーザーが示した好みの項目は一字一句そのまま保存し、既存のほかの好みは残し、好み用のファイルを別に作らない。"
        "ツールでの書き込みが成功してから、覚えたことをユーザーに伝える。"
    ),
)

# 会話 1：ユーザーの好みを保存する
agent.invoke(
    {"messages": [{"role": "user", "content": "私の好みを覚えて：コードのコメントは中国語、変数名は英語"}]},
    context=user,
    config={"configurable": {"thread_id": str(uuid4())}},
)

# Store で書き込み結果を確かめる。モデルが「覚えました」と返したかだけで判断しない。
saved = store.get(namespace, "/preferences.md")
assert saved is not None, "好みのファイルが保存されていません。ツール呼び出しを確認してください"
content = saved.value["content"]
print("保存後の好み：", content)
assert "コードのコメントは中国語" in content and "変数名は英語" in content, "好みが取り決めどおりに書き込まれていません。trace を確認してください"

# 会話 2（まったく新しい会話！）：前に保存した好みを読む
result = agent.invoke(
    {"messages": [{"role": "user", "content": "ソート関数を書いて"}]},
    context=user,
    config={"configurable": {"thread_id": str(uuid4())}},
)
print(result["messages"][-1].content)
```

コード全体を実行し直すたびに新しい `InMemoryStore` が作られ、データは現在のプロセスの中だけに保持される
スレッドをまたぐには Store を使い回す必要があり、プロセスをまたいだり再起動後も残したりするには、この章の後半で扱う永続化 Store が必要

#### 利用シーン

- ユーザーの好みの記憶：ユーザーレベルの名前空間で各ユーザーの好みを区別する
- 自己改善する Agent：ユーザーのフィードバックに応じて自分の指示を更新する
- 知識ベースの蓄積：複数回の会話を通して少しずつ知識ベースを作る
- 研究プロジェクトの継続：Agent が起動時にすべての研究ファイルを読み込み、会話が終わるたびに進捗を更新する。複数の memory パスを使うことで、研究を会話をまたいで進められる

#### 応用的な使い方

**記憶の 6 つの観点**

| 観点 | 中心となる問い | 選択肢 |
| --- | --- | --- |
| 持続期間 | どれくらい残すか？ | 短期（1 回の会話）/ 長期（会話をまたぐ） |
| 情報の種類 | 何を覚えるか？ | エピソード記憶（過去の経験）/ 手続き記憶（Skills）/ 意味記憶（事実） |
| スコープ | 誰が見られるか？ | ユーザーレベル / Agent レベル / 組織レベル |
| 更新戦略 | いつ書き込むか？ | 会話中（デフォルト）/ 会話の合間（バックグラウンドで統合） |
| 検索方法 | どう読むか？ | 起動時に読み込む（memory=）/ 必要に応じて読む（Skills） |
| 権限管理 | Agent は書き込めるか？ | 読み書き（デフォルト）/ 読み取り専用（共有ポリシー） |

**組織レベルの記憶（Organization-level）**

組織レベルの記憶はすべてのユーザーと Agent で共有され、インジェクション攻撃を防ぐため通常は読み取り専用にする
上の `org_namespace()` を使う

**エピソード記憶（Episodic Memory）**

エピソード記憶は過去の経験をまるごと保存し、Agent が「何を学んだか」だけでなく「どう問題を解決したか」も思い出せるようにする
Deep Agents の Checkpointer はもともとエピソード記憶に対応している。過去の会話を検索できるようにするには、検索ツールでラップすればよい

コースと公式ドキュメントの元の例では `query` が使われておらず、何を検索しても同じ結果が返る。しかも `get_history` を使っていて、これはチェックポイントの一覧を返すので、同じ会話が複数のチェックポイントに重複して現れる。以下ではキーワードの文字列一致で探すように変えた。Deep Agents に組み込まれた grep ツールと同じやり方

```python
from langchain.tools import tool, ToolRuntime
from langgraph_sdk import get_client

client = get_client(url="<DEPLOYMENT_URL>")


def current_user_id(runtime: ToolRuntime) -> str:
    if runtime.server_info and runtime.server_info.user:
        return runtime.server_info.user.identity
    user_id = getattr(runtime.context, "user_id", None)
    if user_id:
        return user_id
    raise ValueError("server_info または runtime.context で user_id を指定する必要があります")


@tool
async def search_past_conversations(query: str, runtime: ToolRuntime) -> str:
    """このユーザーの過去の会話から、キーワード query を含むメッセージを探す。文字列一致で探すので、見つからないときは類義語、英語、より短いキーワードに変えて検索し直す。"""
    user_id = current_user_id(runtime)
    current_thread = runtime.config.get("configurable", {}).get("thread_id")
    threads = await client.threads.search(
        metadata={"user_id": user_id},
        limit=5,
        sort_by="updated_at",  # API ドキュメントにデフォルトの順序が定められていないので、明示的に指定する
        sort_order="desc",
    )
    keyword = query.strip().lower()
    if not keyword:
        return "query は空にできません。探したいキーワードを渡して呼び出し直してください。"
    hits = []
    for thread in threads:
        if thread["thread_id"] == current_thread:
            # 進行中の会話は飛ばす
            continue
        # get_state は現在の状態だけを返すので、get_history のような重複は起きない
        state = await client.threads.get_state(thread_id=thread["thread_id"])
        for message in state["values"].get("messages", []):
            content = str(message.get("content", ""))
            if keyword in content.lower():
                hits.append(f"[{thread['thread_id']}] {message.get('type')}: {content[:300]}")
    return "\n".join(hits[:10]) or f"「{query}」を含む過去の会話は見つかりませんでした。"
```

いくつかの補足

- `threads.search()` はメタデータや状態などの条件でスレッドを絞り込めるだけで、テキストでの検索は受け付けないので、クライアント側でメッセージ本文を照合する
- 検索語はモデルが生成するので、言葉づかいが一致する内容しか見つからない。たとえば「エラー」で検索しても「KeyError」とだけ書いた会話は見つからないので、ツールの説明で言葉を変えて検索し直すようモデルに促している
- スレッドの `metadata` にある `user_id` は、アプリがスレッドを作るときに自分で書き込むもので、サーバーは自動で付けない。書き込んでいないとスレッドが 1 つも見つからない
- 現在のスレッドはたいてい最後に更新されたものなので、5 つのうちに含まれる。そのため通常は過去のスレッドが 4 つしか見つからない
- 意味検索が必要な場合は、会話の要約を意味検索を有効にした Store に書き込み（`langgraph.json` で `store.index` を設定する）、`client.store.search_items(namespace, query=query)` で問い合わせる

**バックグラウンドでの記憶の統合（Background Consolidation）**

デフォルトでは Agent は会話中にリアルタイムで記憶を書き込む（ホットパス）。もう 1 つのモードは会話の合間にバックグラウンドで処理するもので、独立した「統合 Agent」をデプロイして最近の会話を見直し、重要な事実を抜き出して記憶ストアにマージする
コードの詳細は
[統合 Agent の例](https://datawhalechina.github.io/deepagents-in-action/chapters/ch08-long-term-memory/#%E5%90%8E%E5%8F%B0%E8%AE%B0%E5%BF%86%E6%95%B4%E5%90%88background-consolidation)
`search_recent_conversations` の `query: str` は不要

**同時書き込み**

Agent レベルや組織レベルの記憶では、バックグラウンドでの統合で書き込みを直列化するか、記憶をテーマごとに独立したファイルに分けて衝突を減らすことを検討する

- テーマごとにファイルを分ける：`/memories/preferences.md`、`/memories/project/tech-stack.md`、`/memories/research/sources.md` を分けておき、複数のスレッドが同時に同じファイルを変更する確率を下げる
- 追記型で記録し、後からバックグラウンドでマージする：会話中はまず `/memories/events/2026-xx-xx-thread-id.md` のような追記ログに書き込み、バックグラウンドの統合 Agent が定期的に重複を除いて安定した記憶ファイルにマージする
- 共有の記憶にはバックグラウンドのタスクだけが書き込む：Agent レベルや組織レベルの記憶はなるべく読み取り専用にし、通常の会話は更新の候補を出すだけにして、バックグラウンドの統合タスクが順番に審査してから書き込む
- 機密性の高い記憶には承認を加える：組織のポリシー、セキュリティルール、長期的な好みの上書きに関わる場合は、Permissions や Human-in-the-Loop で確認なしの直接上書きを防ぐ

### 第 9 章 Human-in-the-Loop：安全な人と Agent の協働フローを作る

Human-in-the-Loop（HITL）：Agent が特定の操作を実行する前に一時停止し、人による承認、修正、拒否、または直接の応答を待ってから実行を続ける

#### `interrupt_on` の設定

```python
from deepagents import create_deep_agent
from langgraph.checkpoint.memory import MemorySaver

# ツールとモデルの定義は省略

# Checkpointer は HITL の必須条件
checkpointer = MemorySaver()

agent = create_deep_agent(
    model=model,
    tools=[delete_file, read_file, send_email],
    interrupt_on={
        # allowed_decisions で選べる操作を指定する
        # 操作は approve / edit / reject / respond の 4 つ
        "delete_file": {"allowed_decisions": ["approve", "edit", "reject"]},
        "read_file": False,    # 中断しない
        "send_email": {"allowed_decisions": ["approve", "reject"]},  # 承認か拒否だけで、修正はできない
    },
    checkpointer=checkpointer,  # 必ず設定する！
)
```

| 決定 | 意味 | 場面 |
| --- | --- | --- |
| approve | 承認して実行する。Agent が提案した元の引数を使う | 「このファイルの削除を確認」 |
| edit | 引数を修正してから実行する | 「宛先を直してから送って」 |
| reject | 今回のツール呼び出しをスキップし、拒否の理由を Agent に返す | 「削除しないで、取り消し」 |
| respond | ツールを実行せず、人の message を成功した合成ツール結果として返す | `ask_user` のような「ユーザーに尋ねる」ツール |

サブ Agent は独自の `interrupt_on` 設定を持つことができ、メイン Agent の設定を上書きする
サブ Agent が機密性の高い操作をする場合は、中断して確認を求めるようにできる

#### 条件付きの中断：本当に危険な呼び出しだけを止める

```python
from deepagents import create_deep_agent
from langchain.agents.middleware import ToolCallRequest
from langgraph.checkpoint.memory import MemorySaver


def writes_outside_workspace(request: ToolCallRequest) -> bool:
    """ワークスペースの外のパスに書き込むときだけ一時停止する。"""
    path = request.tool_call["args"].get("file_path", "")
    return not path.startswith("/workspace/")


agent = create_deep_agent(
    model=model,
    interrupt_on={
        "write_file": {
            "allowed_decisions": ["approve", "edit", "reject"],
            # True を返したときだけ一時停止し、False なら実行する
            "when": writes_outside_workspace,
        },
    },
    checkpointer=MemorySaver(),
)
```

#### 中断と再開

Agent が 1 回の実行の中で中断を設定したツールを呼び出すと、中断して中断の情報を返す
ユーザーはその情報を見て判断したあと、thread_id を使って実行を再開する

```python
import uuid
from langgraph.types import Command

# thread_id を 1 つ作る（再開するときは必ず同じものを使う）
config = {"configurable": {"thread_id": str(uuid.uuid4())}}

# Step 1: リクエストを送る
result = agent.invoke(
    {"messages": [{"role": "user", "content": "temp.txt ファイルを削除して"}]},
    config=config,
    version="v2",
)

# Step 2: 中断したかを確認する
if result.interrupts:
    interrupt_value = result.interrupts[0].value
    action_requests = interrupt_value["action_requests"]
    review_configs = interrupt_value["review_configs"]
    config_map = {cfg["action_name"]: cfg for cfg in review_configs}

    # ユーザーに見せる
    for action in action_requests:
        review_config = config_map[action["name"]]
        args = action.get("arguments", action.get("args", {}))
        print(f"ツール: {action['name']}")
        print(f"引数: {args}")
        print(f"選べる決定: {review_config['allowed_decisions']}")

    # Step 3: ユーザーが決定する
    # message はあらかじめ定義したもの（拒否するときの message）でも、ユーザーの入力でもよい
    decisions = [
        {"type": "approve"}  # ユーザーが削除を承認
    ]
    # decisions = [{
    #     "type": "reject",
    #     "message": "ユーザーがこのファイルの削除を拒否しました。削除を再試行せず、代わりにアーカイブするかを尋ねてください。",
    # }]

    # Step 4: 実行を再開する（必ず同じ config を使う！）
    result = agent.invoke(
        Command(resume={"decisions": decisions}),
        config=config,     # 同じ thread_id
        version="v2",
    )

# 最終結果を取得する
print(result.value["messages"][-1].content)
```

ユーザーが `reject` を返すと、Deep Agents はそのツール呼び出しをスキップし、拒否のフィードバックを Agent に返す
機密性の高いツール（削除など）の場合は、このとき削除を再び要求しないよう明示し、別の操作に切り替えさせるのがよい

#### 複数のツール呼び出しの中断の扱い

```python
# ユーザーのリクエスト：「temp.txt を削除して、admin にメールで知らせて」
result = agent.invoke(
    {"messages": [{"role": "user", "content": "temp.txt を削除して、admin@example.com にメールで知らせて"}]},
    config=config,
    version="v2",
)

if result.interrupts:
    action_requests = result.interrupts[0].value["action_requests"]
    # action_requests[0] = delete_file(path="temp.txt")
    # action_requests[1] = send_email(to="admin@example.com", ...)

    # 順番どおりに決定を渡す
    decisions = [
        {"type": "approve"},  # 削除を承認
        {
            "type": "reject",
            "message": "ユーザーがメールの送信を拒否しました。この送信を再試行しないでください。",
        },
    ]

    result = agent.invoke(
        Command(resume={"decisions": decisions}),
        config=config,
        version="v2",
    )
```
決定の数と順番は一致させる必要がある。`decisions` は `action_requests` と 1 対 1 で対応させ、順番を入れ替えてはいけない

#### リスクレベルごとに推奨される中断の操作

| リスクレベル | ツールの種類 | 設定 | 理由 |
| --- | --- | --- | --- |
| 高リスク | 削除、上書き、送信、デプロイ | `approve`/`edit`/`reject` | 操作が元に戻せない、または外部システムに影響する。`respond` が成功結果と誤解されるのを避ける |
| 中リスク | 書き込み、外部呼び出し | `approve`/`reject` | 承認は必要だが引数の修正は要らない |
| 低リスク | 読み取り、検索、一覧 | `False` | 読み取りだけの操作で、副作用がなく安全 |
| 人の入力型 | 好みを尋ねる、足りない情報を補う | `respond` | もともと人に答えてもらうためのツールで、人の `message` が成功したツール結果になる |

#### ファイルシステムの `mode="interrupt"`

`write_file`、`edit_file`、`delete` が `mode="interrupt"` の権限ルールに当たると、Deep Agents は通常のツール承認と同じ形式の HITL 中断を発生させる

```python
agent = create_deep_agent(
    model=model,
    permissions=[
        FilesystemPermission(
            operations=["write"],
            paths=["/secrets/**"],
            mode="interrupt",
        ),
    ],
    checkpointer=MemorySaver(),
)
# 再開の方法は通常のツールと同じ
```
#### 所感

機密性の高い操作では人の承認が重要だということは、普段いろいろな AI コーディングアシスタントを使っていて実感していた
中断と再開の具体的な操作は初めて知った。もともとは内部でそのまま再開するものだと思っていた
また、学んだことが少しずつ増え、組み合わせて使うものも増えて複雑になってきたので、もっと理解を深める必要があると感じる

## 実践: AI ニュースアシスタントに長期記憶と人による承認を加える

第 8 章と第 9 章を学んだあと、AI ニュースアシスタントに 3 つの変更を加えた：

- 履歴、レポート、長期記憶をすべて SQLite に保存し、namespace をユーザーごとに分ける
- 起動時に `memory=` で記憶ファイル `/memories/preferences.md` を読み込む
- `/history/` と `/report/` に書き込む前に一時停止し、ターミナルで確認してから実行する

リポジトリ: [ryukirin/ai-news-deep-agent](https://github.com/ryukirin/ai-news-deep-agent)

### ユーザーごとの namespace

| Agent から見たパス | バックエンド | 実際の保存先 |
| --- | --- | --- |
| `/history/news_history.txt` | `StoreBackend` | `news.db` の `store` テーブル、namespace は `(ユーザー, "history")` |
| `/report/<日付>.md` | `StoreBackend` | `news.db` の `store` テーブル、namespace は `(ユーザー, "report")` |
| `/memories/` 以下のパス | `StoreBackend` | `news.db` の `store` テーブル、namespace は `(ユーザー, "memories")` |
| `/skills/` 以下のパス | `FilesystemBackend` | プロジェクトの `skills/` ディレクトリ、読み取り専用 |
| その他のパス | `StateBackend` | Agent の state。実行が終わると残らない |

ユーザーは `identity.py` の `user_namespace` で決まる。書き方は上のユーザーレベルの記憶にある `user_namespace` と同じ：

```python
# 当面はすべて local-user をユーザーとして扱う
def user_namespace(rt):
    if rt.server_info and rt.server_info.user:
        return (rt.server_info.user.identity,)
    user_id = getattr(rt.context, "user_id", "local-user")
    return (user_id,)
```

`context_schema` に使う `MemoryContext` は `memory_model.py` に書いた：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class MemoryContext:
    user_id: str = "local-user"
```

- `rt.server_info.user` があればその `identity` を使い、なければ context の `user_id` を使う。`invoke` で context を渡していないので、今はユーザーが `local-user` に固定されている
- Task5 の版では、`/history/` の namespace は `("local-user",)` で、レポートは `FilesystemBackend` でプロジェクトの `report/` ディレクトリに書き込んでいた。今は 3 種類のデータをすべて `(ユーザー, 用途)` の下に置き、レポートも `news.db` に保存している

レポートはファイルとして書き出さなくなったので、ある日のレポートはプロジェクトのルートで次のコードを使って読む：

```python
from langgraph.store.sqlite import SqliteStore

with SqliteStore.from_conn_string("news.db") as store:
    item = store.get(("local-user", "report"), "/2026-10-29.md")
    print(item.value["content"])
```

### 長期記憶

- `memory=["/memories/preferences.md"]` は起動時にこのファイルの内容をシステムプロンプトに入れる
- `memory=` は既存のファイルを読み込むだけで、`/memories/preferences.md` を自動では作らない
- Agent が自分で記憶を書くとき、ファイル名はモデルが決める。10 月 29 日のある実行では `/memories/workflow_notes.md` に書き込んだが、このパスは `memory=` のリストにないので、次の実行では読み込まれない

### 書き込み前の人による承認

承認が必要なパスは `agent.py` の `protected_path` で判定する：

```python
def protected_path(request):
    """承認が必要な操作のパスを定める"""
    path = request.tool_call["args"].get("file_path", "")
    try:
        path = validate_path(path)
    except ValueError:
        return False
    return path.startswith(("/history/", "/report/"))
```

- `interrupt_on` で `write_file`、`edit_file`、`delete` のすべてに `when=protected_path` を設定し、対象が `/history/` か `/report/` の下にあるときだけ一時停止する。それ以外のパス（`/memories/` を含む）への書き込みでは一時停止しない
- `protected_path` はまず `validate_path` でパスを正規化し、正規化に失敗したら `False` を返して一時停止しない
- `allowed_decisions` で許可しているのは `approve` と `reject` だけ
- サブ Agent の中で起きた書き込みの呼び出しも同じように一時停止する
- 実行の再開には同じ `thread_id` が必要なので、Checkpointer の `MemorySaver` を加え、実行のたびに `uuid4` で新しい `thread_id` を作る

一時停止すると、`ask_user.py` の `ask_decision` がコマンドラインから決定を読み取る：

```python
import json

def ask_decision(action, allowed):
    name = action["name"]
    args = action.get("arguments", action.get("args", {}))
    print(f"\nツール: {name}\n引数: {json.dumps(args, ensure_ascii=False)}\n選べる決定: {', '.join(allowed)}")
    while True:                                    # 許可された範囲外の入力なら入力し直す
        choice = input("決定を入力してください: ").strip()
        if choice in allowed:
            break
        print(f"{', '.join(allowed)} のいずれかしか入力できません")

    if choice == "approve":
        return {"type": "approve"}
    if choice == "edit":                           # 引数を 1 つずつ尋ね、そのまま Enter なら元の値を残す
        new_args = {}
        for key, value in args.items():
            text = input(f"  {key}（そのまま Enter で {value!r} を残す）: ").strip()
            new_args[key] = text if text else value
        return {"type": "edit", "edited_action": {"name": name, "args": new_args}}
    if choice == "reject":                         # 理由は空でもよく、空のときはミドルウェアのデフォルトのフィードバックを使う
        decision = {"type": "reject"}
        reason = input("拒否の理由（空でも可）: ").strip()
        if reason:
            decision["message"] = reason
        return decision
    return {"type": "respond", "message": input("回答: ").strip()}
```

- 入力が `allowed_decisions` にないときは入力し直させる
- `reject` のあとに拒否の理由を入力でき、理由は `message` としてモデルに返される。空のときはミドルウェアのデフォルトのフィードバックを使う
- `edit` と `respond` の分岐は今は使われない。`allowed_decisions` にこの 2 つが入っていないため

### Agent

`agent.py` のうち、Agent を作って実行する部分：
