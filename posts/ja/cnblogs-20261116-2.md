## ノート - 第 4 章 エージェントの古典的なパラダイムの構築

### 代表的な 3 つのアーキテクチャパラダイム

- ReAct: まず考え、次に行動し、その結果を観察して次の行動を決める。全体はループの中で進む
- Plan-and-Solve: 先に計画を立ててから、ステップごとに実行する
- Reflection: 振り返りによって結果を改善する

#### 既存フレームワークの制約

- 抽象度が高く、さまざまなロジックが殻の中に閉じ込められ、ユーザーには外部インターフェースしか残されていないので、動作の仕組みを深く理解できない
- まだ安定していないフレームワークでは、破壊的な変更が起きやすい
- 高度なカスタマイズが必要な場面では、自分で一から作るほうが手っ取り早い

### ReAct

- Thought（思考）: 考える
- Action（行動）: どの行動をとるかを決める
- Observation（観察）: 行動を実行し、結果を返す

適した場面

- 外部の知識が必要なタスク
- 正確な計算が必要なタスク
- API とのやり取りが必要なタスク

#### 特徴

- 思考の過程を観察でき、透明性が高いので、改善点を見つけやすい
- 動的な計画能力があり、結果に応じて計画（次のステップ）を変えられる

#### 制約

- LLM の能力に依存する
- 実行に時間がかかり、コストも高い
- プロンプトに依存する
- 局所最適に陥りやすく、長期的な計画能力がなく、袋小路にはまることもある

### Plan-and-Solve

先に計画を立ててから実行する

プランナー `Planner` が plan を生成し、エグゼキューター `Executor` がタスクを実行して状態を管理する

そのためエグゼキューターは、計画全体、各ステップの実行結果、現在の進み具合を保持する必要がある

プロンプトの例

```python
EXECUTOR_PROMPT_TEMPLATE = """
あなたは一流の AI 実行エキスパートです。与えられた計画に厳密に従い、一歩ずつ問題を解決するのがあなたのタスクです。
元の問題、計画全体、そしてこれまでに完了したステップとその結果を受け取ります。
「現在のステップ」の解決に集中し、そのステップの最終的な答えだけを出力してください。余計な説明や会話は出力しないでください。

# 元の問題:
{question}

# 計画全体:
{plan}

# これまでのステップと結果:
{history}

# 現在のステップ:
{current_step}

「現在のステップ」に対する回答だけを出力してください:
"""
```

#### 制約

最初の計画が重要で、計画を誤るとその後もずっと誤り続ける

### Reflection

自己チェックのパターン。まずタスクを完了させ、次に自分でレビューし、そのレビュー結果にもとづいて改善する

これもループの中で進み、新しい問題がなくなるまで続く -> そのため無限ループに陥る可能性があり、最大ループ回数を設定しておくのがよい

上の 2 つのパラダイムと組み合わせて使える

## 練習問題

1. この章では、ReAct、Plan-and-Solve、Reflection という 3 つの古典的なエージェントパラダイムを紹介した。次の点を分析せよ:
   - この 3 つのパラダイムは、「思考」と「行動」の組み立て方において本質的に何が違うか？
     - ReAct は実行の各ステップに 1 回の思考がともなう
     - Plan-and-Solve は先に 1 回考えて計画を立て、その後は計画に沿って行動する
     - Reflection は先に実行してから考える。ただし実行の部分は他のパラダイムと組み合わせられ、そこでも思考が入る
   - 「スマートホーム制御アシスタント」（照明、エアコン、カーテンなど複数の機器を制御し、ユーザーの習慣に合わせて自動で調整する）を設計するとしたら、どのパラダイムを基本アーキテクチャに選ぶか？その理由は？
     - ReAct。多くのツールを呼び出す必要があって ReAct と相性がよく、ユーザーの習慣に合っているかどうかをいつでも考えられるから
   - この 3 つのパラダイムを組み合わせて使えるか？使えるなら、パラダイムを組み合わせたエージェントのアーキテクチャを設計し、その適用場面を説明せよ。
     - reviewer agent。主な適用場面は資料やコードのレビュー。
       - まずコード全体の規模と概要を見て、ルールや設計書があるか、ユーザーからの要求があるかを確認し、それらを前提にレビュー計画を作る
       - 次に一歩ずつ実行し、実行中にレビュー結果を観察して、妥当かどうか、外部資料やデータベースの参照を申請すべきかを分析する
       - 最後にレビュー結果をもう一度評価し、agent 自身がほかに問題がないと判断したら終了する

2. 4.2 節の ReAct の実装では、正規表現で大規模言語モデルの出力（Thought や Action など）を解析した。次の点を考えよ:
   - 現在の解析方法にはどのような脆さがあるか？どのような場合に失敗しうるか？
     - LLM の出力は安定しない。プロンプトの指示どおりに出力せず、マッチしない文字列を出力すると、内容を取り出せなくなる
     - マッチしても誤った内容を取り出すことがある。[Task0](https://ryukirin.github.io/blog/post.html?slug=cnblogs-20261116&lang=ja#%E7%AC%AC-4-%E7%AB%A0%E3%81%AE%E3%82%B3%E3%83%BC%E3%83%89) のステップ 4 がその例
       - `_parse_output` は `Action:\s*(.*?)$` と `re.DOTALL` で Action を取り出すので、最初の `Action:` から末尾までのテキストがすべて Action として扱われる
       - モデルが Action の後に Observation を自分で作り、さらに次の Action と Finish まで書いた。`_parse_action` は最初の `[` から最後の `]` までの全文を検索語として SerpApi に渡し、検索は `Expecting value: line 1 column 1 (char 0)` で失敗した
       - このテキストはエラーと一緒に history に書き込まれ、ステップ 5 でモデルはそれをもとに最終回答を出した。回答にある発表日と 6.8 インチ 16:10 の画面は、モデルが自分で作った内容にしか出てこず、検索結果には含まれていない
   - 正規表現のほかに、より堅牢な出力解析の方法には何があるか？
     - JSON 形式での出力に切り替え、Pydantic で検証し、失敗したらエラーをモデルに返して再試行させる
   - この章のコードを修正してより信頼性の高い出力形式を使い、2 つの方法の長所と短所を比較せよ
     - `response` の生成時に `response_format` パラメータを追加し、`json.loads(text)` で `thought`、`action`、`action_input` を解析する。失敗したときはエラーの原因をモデルに見せる
     - テストの結果、JSON の解析は比較的安定していたが、モデルが `response_format` に対応している必要がある

3. ツール呼び出しは現代のエージェントの中核的な能力の 1 つである。4.2.2 節の ToolExecutor の設計をもとに、次の拡張課題に取り組め:
   > ヒント: これは手を動かす実践問題なので、実際にコードを書くことをすすめる
   - ReAct エージェントに「電卓」ツールを追加し、複雑な数学の計算問題（「(123 + 456) × 789/ 12 = ? を計算せよ」など）を扱えるようにする
      ```python
      import re

      def calculator(expression: str) -> str:
          """
          四則演算を行うツール
          数式を計算し、エラー時は計算エラーを返す
          """
          print(f"🧮 [Calculator] 計算を実行中: {expression}")
          # Python で実行できる式に変換する
          expression = expression.replace("×", "*").replace("÷", "/")
          # 四則演算かどうかをチェックする
          if not re.fullmatch(r"[\d\s.+\-*/()]+", expression) or "**" in expression:
              return "計算エラー：数字、+ - * /、括弧にのみ対応しています"
          try:
              return str(eval(expression))
          except ZeroDivisionError:
              return "計算エラー：0 で割ることはできません"
          except Exception:
              return "計算エラー：式の形式が正しくありません"
      # ReAct.py
      calculator_desc = "電卓。加減乗除の計算が必要なときに使う。入力に使えるのは数字、+ - * /、括弧のみ"
      tool_executor.registerTool("Calculator", calculator_desc, calculator)
      agent = ReActAgent(llm_client=llm, tool_executor=tool_executor)
      question = "(123 + 456) × 789 / 12 = ? の結果を計算してください"
      agent.run(question)
      ```

     - エラー情報を LLM に開示する
   - 考察: 呼び出せるツールの数が 50 個、さらには 100 個に増えたとき、現在のツールの記述方法は有効に機能するか？業務のニーズに応じてツールの数が大きく増えたとき、エンジニアリングの観点からツールの整理と検索の仕組みをどう最適化するか？
     - 機能しない。ツールの名前と説明だけでもコンテキストのかなりの部分を占め、注意が分散するうえ、モデルがどのツールを使うべきか判断しにくくなる

4. Plan-and-Solve パラダイムはタスクを「計画」と「実行」の 2 段階に分ける。次の点を深く分析せよ:
   - 4.3 節の実装では、計画段階で生成される計画は「静的」（一度に生成され、変更できない）である。実行中にあるステップが完了できない、または結果が期待どおりでないとわかった場合、「動的な再計画」の仕組みをどう設計すべきか？
     - Planner をツールにして ReAct を使い、期待どおりでないと観察したときに Planner をもう一度呼び出して、調整した計画を生成する
   - Plan-and-Solve と ReAct を比較せよ: 「北京から上海への出張の予約（航空券、ホテル、レンタカーを含む）」のようなタスクを処理するとき、どちらのパラダイムが適しているか？その理由は？
     - Plan-and-Solve でさまざまな条件から先に計画を立て、その後予約を実行する。ただし予約のステップはトラブルが起きやすいので、ReAct を加えて 2 つを組み合わせて使うのがよい
   - 「階層的な計画」システムを設計せよ: まず高レベルの抽象的な計画を生成し、次に高レベルの各ステップについて詳細なサブ計画を生成する。この設計にはどのような利点があるか？
     - まず各ステップの大まかな方向性を示す計画を書き、実行するときに前のステップの結果を分析して、細かい計画に分けていきたい
     - 各ステップの実行コマンドを固定しないので、ある程度改善の余地が残る

5. Reflection の仕組みは「実行-振り返り-改善」のループで出力の品質を高める。次の点を考えよ:
   - 4.4 節のコード生成の例では、各段階で同じモデルを使っている。2 つの異なるモデルを使った場合（たとえば、より強力なモデルで振り返りを行い、より速いモデルで実行する）、どのような影響があるか？
     - 効率と信頼性を高めつつ、コストも抑えられる
       - 異なる 2 つのモデルなら、自分の回答を認めがちになる問題が起きない
       - 速いモデルで実行すれば効率が上がり、token の消費も減るかもしれない
       - 強力なモデルで振り返れば、正確さをある程度担保できる
   - Reflection の仕組みの終了条件は「フィードバックに『改善不要』が含まれる」か「最大反復回数に達する」である。この設計は妥当か？よりスマートな終了条件を設計できるか？
     - 妥当ではない。「改善不要」はあいまいすぎて、実際には最大反復回数に達して終了する可能性が高い
     - タスクに応じて受け入れ条件を設計し、その条件を満たしたら今回のレビューを終える
   - 「学術論文執筆アシスタント」を作るとする。初稿を生成し、論文の内容を改善し続けられるものである。段落の論理性、手法の新規性、言語表現、引用の規範など複数の観点から振り返りと改善を行う、多次元の Reflection の仕組みを設計せよ。
     - 段落の論理性：各段落に中心文があるか、主張と根拠が対応しているか、前後で矛盾していないか
     - 手法の新規性：関連論文や既存手法を検索し、中核となる新規性と似た内容を確認して、両者を比較したうえで重点についての評価を出す
     - 言語表現：口語的になっていないか、用語が前後で一貫しているか、学術的な文章の水準に達しているか
     - 引用の規範：まず必要な引用形式を確認し、本文中の引用と参考文献が一対一で対応しているか、各項目のフィールドがそろっているか、文献が実在するかをチェックする
     - 挙がった問題を深刻度で分類し、最も深刻なものから修正する

6. プロンプトエンジニアリングは、エージェントの最終的な効果を左右する重要な技術である。この章では、よく設計されたプロンプトテンプレートを複数示した。次の点を分析せよ:
   - 4.2.3 節の ReAct のプロンプトと 4.3.2 節の Plan-and-Solve のプロンプトには、構造の設計に明らかな違いがある。これらの違いは、それぞれのパラダイムの中核となるロジックにどう役立っているか？
     - ReAct：Thought と Action を分け、実行時にはツールを選ぶか最終回答を生成するかのどちらかを求める
     - Plan-and-Solve：先に計画を生成してからタスクを実行するよう求め、順序はコードで決まっている
   - 4.4.3 節の Reflection のプロンプトでは、「あなたは極めて厳格なコードレビューの専門家です」という役割設定を使った。この役割設定を変えて（たとえば「あなたはコードの可読性を重視するオープンソースプロジェクトのメンテナーです」に変える）、出力結果の変化を観察し、役割設定がエージェントの振る舞いに与える影響をまとめよ。
     - 役割設定を変えて一度実行してみたところ、終了条件についてのエージェントの判断に影響することがわかった。極めて厳格な設定では修正を何度も試み、まだより良い解があると考える傾向が強い。コードの可読性を重視する設定では、いくつかの案から選ぶときに可読性を判断基準にし、厳格な設定と比べると今の結果を受け入れる傾向がやや強い
   - プロンプトに few-shot の例を加えると、特定の形式に従うモデルの能力が大きく上がることが多い。この章のいずれかのエージェントに few-shot の例を加えてみて、その効果を比較せよ。
      ```
      以下の 2 つの例は、各ラウンドでどのように応答すべきかを示しています：

      例 1
      Question: エッフェル塔の高さは？
      History:
      あなたの応答：
      Thought: これは事実に関する質問なので、まずエッフェル塔の高さを検索する必要がある。
      Action: Search[エッフェル塔 高さ]

      例 2
      Question: エッフェル塔の高さは？
      History:
      Action: Search[エッフェル塔 高さ]
      Observation: エッフェル塔の高さは 330 メートル（アンテナを含む）。
      あなたの応答：
      Thought: 検索結果に高さが示されており、質問に答えるのに十分な情報がある。
      Action: Finish[エッフェル塔の高さは約 330 メートル（アンテナを含む）。]
      ```
      ReAct に few-shot を追加した。元のプロンプトでは 1 件の応答で Thought が抜けていたが、追加後はすべての応答に Thought が書かれていた

7. ある EC スタートアップが、「カスタマーサービスエージェント」で人間のカスタマーサポートを置き換え、コスト削減と効率化を図りたいと考えている。このエージェントには次の機能が必要である:

   - a. ユーザーの返金申請の理由を理解する
   - b. ユーザーの注文情報と配送状況を照会する
   - c. 会社のポリシーにもとづいて、返金を承認すべきかどうかを賢く判断する
   - d. 適切な返信メールを作成し、ユーザーのメールアドレスに送信する
   - e. 判断に議論の余地がある場合（自己の確信度がしきい値を下回る場合）、自分の判断を振り返り、より慎重な提案ができる

   このプロダクトの責任者として:

   - この章のどのパラダイム（またはどのパラダイムの組み合わせ）をシステムの中核アーキテクチャに選ぶか？
     - ReAct と Reflection。ワークフローが決まっているので、事前に計画を立てる必要はない
   - このシステムにはどのようなツールが必要か？少なくとも 3 つのツールとその機能を挙げよ。
     - `get_order`：ユーザーが注文について問い合わせたとき、ユーザー ID で注文情報を照会するツール
     - `get_logistics`：注文の配送状況を照会するときに使うツール
     - `search_policy`：関連する返金ポリシーを調べるときに使うツール
     - `send_email`：メールを送信するツール
   - エージェントの判断が会社の利益に沿いつつ、ユーザーへの親しみやすい態度も保てるよう、プロンプトをどう設計するか？
      ```
      あなたは経験豊富で、ユーザーに親切な返金審査担当者です。ポリシーの条項と注文の事実だけにもとづいて判断します

      # 手順
      1. ユーザーのメッセージから返金の理由を理解する
      2. 注文と配送の情報を集める
      3. 関連する返金ポリシーを調べる
      4. 返金するかどうかを決める
      5. 判断が正しいかを振り返る
      6. 親しみやすい語調のメールを書く
      7. ユーザーのメールアドレスに送信する

      # ユーザーからのメッセージ
      <user_message>
      {user_message}
      </user_message>

      # 出力の要件
      すべての結論で条項番号と事実を引用すること。ユーザーしか提供できない情報（商品の写真など）が足りない場合は need_info を出力する。ポリシーでカバーされていないケースでは escalate を出力する。

      JSON で出力する：
      {
        "decision": "approve | reject | need_info | escalate",
        "clause_ids": ["引用した条項番号"],
        "evidence": ["判断を裏づける具体的な事実"],
        "confidence": 0 から 1 の数値,
        "reason_for_user": "ユーザーに見せる一文の理由"
      }
      ```

     - 個人情報の漏えい：注文や配送の情報をモデルに渡す前に、個人情報をマスキングする
