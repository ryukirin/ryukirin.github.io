## What a decorator is

If you are interested, see the original PEP 318, [Decorators for Functions and Methods](https://peps.python.org/pep-0318/). It explains what the syntax is for and why decorators were designed.

> The current method for transforming functions and methods (for instance, declaring them as a class or static method) is awkward and can lead to code that is difficult to understand. Ideally, these transformations should be made at the same point in the code where the declaration itself is made. This PEP introduces new syntax for transformations of a function or method declaration.

According to the example in the PEP,

```
@dec2
@dec1
def func(arg1, arg2, ...):
    pass
```

is equivalent to

```
def func(arg1, arg2, ...):
    pass
func = dec2(dec1(func))
```

## Usage

### Closures

This is only a brief introduction. For details, see [理解Python闭包概念](https://www.cnblogs.com/yssjun/p/9887239.html).

What makes a closure: a function defined inside another function remembers the environment it was created in, including any variables available in the outer function's scope.

```
def outer_function(message):
    msg = [message]
    def inner_function(person):
        msg.append(person)
        print(msg)
    return inner_function

closure = outer_function("Hello, World!")
closure("x")
closure("y")
------------------------------------------
['Hello, World!', 'x']
['Hello, World!', 'x', 'y']
```

#### Closures and object-oriented programming

Closures are concise and an important part of functional programming, but they are less readable.

Object-oriented code handles more complex scenarios easily through attributes, but it can be heavyweight.

#### Notes

**Mutable and immutable types**

See [可变与不可变类型](https://www.cnblogs.com/superwuchaofan/p/16562454.html)

> The built-in function `id()` returns the memory address of a value.
>
> A mutable object can change its value while its `id()` stays the same.<br>
> Among the basic data types, lists, sets, and dictionaries are mutable.
>
> If changing an object's value requires creating a new object, the object is immutable.<br>
> Among the basic data types, numbers, strings, and tuples are immutable.

##### Variable references

An inner function can access the outer function's variables. It can modify mutable data types (such as lists and dictionaries) but cannot modify immutable ones (such as numbers, strings, and tuples).<br>
My understanding is that the inner function cannot change the address the outer variable points to, but it can modify the value in place.

```
def outer_function(message):
    msg = message
    def inner_function(person):
        msg += person
        print(msg)
    return inner_function

closure = outer_function("Hello, World!")
closure("x")
closure("y")
------------------------------------------
    msg += person
    ^^^
UnboundLocalError: cannot access local variable 'msg' where it is not associated with a value
```

`nonlocal` tells Python that the variable comes from the outer function.

```
def outer_function(message):
    msg = message
    def inner_function(person):
        nonlocal msg
        msg += person
        print(msg)
    return inner_function

closure = outer_function("Hello, World!")
closure("x")
closure("y")
------------------------------------------
Hello, World!x
Hello, World!xy
```

##### The closure pitfall

Here is the classic example.

```
# The intent is to record the square of i in each iteration
def my_func(*args):
    fs = []
    for i in range(3):
        def func():
            return i * i
        fs.append(func)
    return fs

# Following that idea, the expected output is 0 1 4
# The actual output is 4 4 4
fs1, fs2, fs3 = my_func()
print(fs1())
print(fs2())
print(fs3())
```

The blog post [循环变量与闭包](https://suborbit.net/posts/loopvar-and-closure/) explains it this way:

> In Python, only modules, classes, and functions (def, lambda) introduce a new scope. Other code blocks (such as `if`, `for`, and `while`) do not. Python closures also capture variables by reference, so we can already guess that the outputs end up being the same value.

Compared with the other languages in that post, the explanation is that Python reuses the loop variable, and a closure captures the variable by pointing to its address, much like a pointer.<br>
So no new variable is created. The old variable keeps changing at the same address as the loop runs, and what gets appended to fs is a variable that changes along with the value stored at that address.<br>
When the loop finishes, every result becomes 4.

For this reason, use a lambda, which creates a new scope:

```
def my_func(*args):
    fs = []
    for i in range(3):
        fs.append((lambda x=i: x * x))
    return fs


fs1, fs2, fs3 = my_func()
print(fs1())
print(fs2())
print(fs3())
```

> A returned closure should not reference any loop variable or any variable that changes later.

### Decorators

> A decorator is one application of closures

An example is the most direct way to see it, so here is the full code first.

```
from functools import wraps


def the_first(fn):
    @wraps(fn)
    def firstly_wrapped():
        """wrapped in the first function"""
        print("in firstly_wrapped")
        print(fn.__name__)
        print(fn.__doc__)
        return 'here is the first function - ' + fn()

    return firstly_wrapped


def the_second(fn):
    @wraps(fn)
    def second_wrapped():
        """wrapped in the second function"""
        print("in second_wrapped")
        print(fn.__name__)
        print(fn.__doc__)
        return 'here is the second function - ' + fn()

    return second_wrapped


@the_first
@the_second
def hello_world():
    """hello with two decoration"""
    return "Hello World"


print(hello_world())
-------------------------------------------------------------
in firstly_wrapped # Printed text in firstly_wrapped
hello_world # fn.__name__ printed in firstly_wrapped
hello with two decoration # fn.__doc__ printed in firstly_wrapped (the text in """""" under def)
in second_wrapped # Printed text in second_wrapped
hello_world # fn.__name__ printed in second_wrapped
hello with two decoration # fn.__doc__ printed in second_wrapped
here is the first function - here is the second function - Hello World # Return value of hello_world
```

First, the `hello_world` part:

```
@the_first
@the_second
def hello_world():
    """hello with two decoration"""
    return "Hello World"

print(hello_world())
```

The two decorators are equivalent to

```
the_first(the_second(hello_world))
```

The execution order is `the_first` → `the_second` → `hello_world`.

Next, `@wraps(fn)`. This decorator keeps `hello_world` from being overwritten. With both `@wraps(fn)` lines commented out, the output becomes:

```
in firstly_wrapped # Printed text in firstly_wrapped
second_wrapped # fn.__name__ printed in firstly_wrapped
wrapped in the second function # fn.__doc__ printed in firstly_wrapped
in second_wrapped # Printed text in second_wrapped
hello_world # fn.__name__ printed in second_wrapped
hello with two decoration # fn.__doc__ printed in second_wrapped
here is the first function - here is the second function - Hello World # Return value of hello_world
```

The main difference from the first output is

```
second_wrapped # fn.__name__ printed in firstly_wrapped
wrapped in the second function # fn.__doc__ printed in firstly_wrapped
```

This happens because what gets passed into `firstly_wrapped` is no longer `hello_world` but `second_wrapped`, which has replaced `hello_world`.

> The `@wraps` decorator preserves the wrapped function's metadata, such as its name, docstring, and signature.

Think of it as copying `fn`'s information onto `firstly_wrapped`, so every `fn` inside that function refers to `fn` itself and is not overwritten.
