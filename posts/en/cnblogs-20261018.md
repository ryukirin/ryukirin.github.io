### Chapter 4 Task Planning and Decomposition: Teaching the Agent to Break Down Complex Tasks

#### The three todo states

| State       | Meaning     | Typical case                                          |
| ----------- | ----------- | ----------------------------------------------------- |
| pending     | To do       | The agent has just planned it and has not started yet |
| in_progress | In progress | The agent is working on this step                     |
| completed   | Done        | The agent has marked the task as done                 |

An example of the agent updating its todos:

Calling `write_todos`

- To continue the list automatically across multiple `invoke()` calls, configure a Checkpointer and reuse the same `thread_id`. Adding `TodoListMiddleware` alone does not carry over the state of the previous run
- `InMemorySaver` keeps checkpoints only in the current process. To restore them after the process restarts, use a persistent Checkpointer backed by a database or similar storage. When the agent is deployed to Agent Server, the platform provides the persistence
- Subagents declared with `subagents=[...]` have their own middleware stack. A subagent that needs planning must enable Todo in its own spec, and it does not read the main agent's list

#### LangChain middleware

What `create_deep_agent()` does internally is, in essence, assemble a set of middleware onto the agent automatically

**Two kinds of hooks**

| Style      | Hooks                                                         | How it runs                                                                                   | Good for                                                 |
| ---------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Node-style | `before_agent`, `before_model`, `after_model`, `after_agent` | Compiled into separate nodes in the agent graph and run in lifecycle order                    | Validation, state updates, auditing, human interrupts    |
| Wrap-style | `wrap_model_call`, `wrap_tool_call`                           | Wraps a single model or tool call; it can call `handler` zero times, once, or several times | Retries, caching, fallbacks, request or response changes |

Node-style hooks have clear graph node boundaries, so they are the better place to set a human interrupt with `interrupt()`

**Default middleware**

- `FilesystemMiddleware`: injects the 7 file tools and enforces the permissions rules
- `SummarizationMiddleware`: compresses the context automatically, with a configurable trigger threshold
- `PatchToolCallsMiddleware`: fills in tool responses that are missing from the message history
- Model-related capabilities such as prompt caching: whether they are enabled depends on the model and the harness profile

**Middleware configured by parameters**

- `SubAgentMiddleware`: configured by `subagents=`, includes the general-purpose subagent by default, and provides the task tool
- `SkillsMiddleware`: enabled when `skills=` is passed, and injects skill packages
- `AsyncSubAgentMiddleware`: enabled when async subagents are passed
- `MemoryMiddleware`: enabled when `memory=` is passed, and injects AGENTS.md memory
- `HumanInTheLoopMiddleware`: enabled when `interrupt_on=` is passed, and holds the specified tool calls for human approval

**Middleware configured with `middleware=[...]`**

- Optional policies such as `TodoListMiddleware` can be added as needed
- An instance with the same name as a default middleware replaces the default instance in its original position, and no second copy is added at the end
- This in-place replacement swaps the whole instance and does not merge the old and new settings field by field


| Category   | Middleware               | Purpose                                                             |
| ---------- | ------------------------ | ------------------------------------------------------------------- |
| Planning   | TodoListMiddleware       | Task planning and tracking; injects write_todos and the todos state |
| Safety     | PIIMiddleware            | Detects and masks personal information                              |
| Resilience | ToolRetryMiddleware      | Retries failed tool calls automatically                             |
| Resilience | ModelRetryMiddleware     | Retries failed model calls automatically                            |
| Resilience | ModelFallbackMiddleware  | Switches to a backup model when the main model fails                |
| Limits     | ToolCallLimitMiddleware  | Limits the number of tool calls                                     |
| Limits     | ModelCallLimitMiddleware | Limits the number of model calls                                    |
| Context    | ContextEditingMiddleware | Clears old tool call results                                        |

#### PatchToolCallsMiddleware (Node-style)

Suppose the message history contains a tool call request with no matching tool response, for example because a run was cancelled or the arguments were broken. On the next run, `PatchToolCallsMiddleware` checks the history in the `before_agent` hook and adds a `ToolMessage` for each missing response, saying that the call was cancelled. For calls whose arguments were broken or truncated, the message says that the call could not be executed.

```python
from langchain_core.messages import AIMessage
from langgraph.checkpoint.memory import InMemorySaver

# A test model from the deepagents-in-action course project; it returns the replies preset in responses, in order
from course_notebooks.testing import ScriptedChatModel
from deepagents import create_deep_agent

executed = []  # Records whether echo actually ran


def echo(text: str) -> str:
    """Return the text unchanged."""
    executed.append(text)
    return f"echo: {text}"


model = ScriptedChatModel(responses=[
    AIMessage(content="", tool_calls=[{"name": "echo", "args": {"text": "hello"}, "id": "call_1"}]),
    AIMessage(content="Reply from the second run"),
])
agent = create_deep_agent(model=model, tools=[echo], checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "demo"}}


def show(title):
    """
    Print the messages saved in the checkpoint
    args:
        title: heading for this printout
    return:
        None
    """
    print(f"\n== {title}")
    for m in agent.get_state(config).values["messages"]:
        calls = [c["id"] for c in getattr(m, "tool_calls", [])]
        extra = f" tool_calls={calls}" if calls else ""
        extra += f" tool_call_id={m.tool_call_id} status={m.status}" if m.type == "tool" else ""
        print(f"  {m.type:<6}{extra}  {str(m.content)[:60]!r}")


# First run: stop as soon as the model node finishes, simulating a user cancel, a process crash, a timeout, and so on
for update in agent.stream({"messages": [{"role": "user", "content": "echo hello"}]}, config, stream_mode="updates"):
    print("Completed node:", list(update))
    if "model" in update:
        break

show("Messages in the checkpoint after the first run was cancelled")
print("  echo executions:", len(executed))

# Second run: with the same thread_id, before_agent checks the history first and fills in the missing tool response
agent.invoke({"messages": [{"role": "user", "content": "continue"}]}, config)
show("Messages in the checkpoint after the second run")
print("  echo executions:", len(executed))
------------------------------------------
Completed node: ['PatchToolCallsMiddleware.before_agent']
Completed node: ['model']

== Messages in the checkpoint after the first run was cancelled
  human   'echo hello'
  ai     tool_calls=['call_1']  ''
  echo executions: 0

== Messages in the checkpoint after the second run
  human   'echo hello'
  ai     tool_calls=['call_1']  ''
  tool   tool_call_id=call_1 status=error  'Tool call echo with id call_1 did not complete - no result w'
  human   'continue'
  ai      'Reply from the second run'
  echo executions: 0
```

`tool   tool_call_id=call_1 status=error  'Tool call echo with id call_1 did not complete - no result w'` is the `ToolMessage` that was filled in

How different problems during a run are handled:


| Situation                                              | Handled by                                                   | What to watch for                                                                                                    |
| ------------------------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| The history has a tool call but no matching response   | `PatchToolCallsMiddleware` adds an explanatory message      | It does not retry the tool or check whether the result is correct                                                   |
| A tool call hits a retryable exception                 | `ToolRetryMiddleware`, if the application configures it      | The policy decides whether to retry and how many times; for write operations, also consider duplicate execution      |
| The next run continues from the previous state         | A Checkpointer with the same `thread_id`                     | Restoring across processes requires a persistent Checkpointer                                                       |
| A tool returned content, but is the content correct?   | The application's validation, evaluation, or human review   | A successful call or a completed list does not mean the result is correct                                           |

#### TodoListMiddleware (uses both styles)

- `wrap_model_call`: adds the planning prompt to the request each time the model is called
- `after_model`: after the model replies, checks whether that reply calls `write_todos` several times in parallel, and returns an error if it does


`write_todos` is implemented by LangChain's `TodoListMiddleware`. Once it is added, the agent automatically gets:

- The `write_todos` tool: creates and manages the task list
- The `todos` state: stores the tasks and their status for later steps and the UI; continuing across calls is handled by the Checkpointer
- A planning guidance prompt: guides the agent to plan before acting when it faces a complex task

**Custom configuration**

`TodoListMiddleware` accepts the following two parameters
```python
TodoListMiddleware(
    system_prompt="...",      # Custom planning guidance prompt
    tool_description="...",   # Custom description of the write_todos tool
)
```

#### SummarizationMiddleware (Wrap-style)

Handles context compression.

To read the history back by path, you also need a `FilesystemMiddleware` that uses the same backend. The `compact_conversation` tool (manual compression) comes from a separate `SummarizationToolMiddleware`, which is configured separately from the automatic summarization described here.

The summarization threshold is set automatically, and you can override it if you want.

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.middleware.summarization import SummarizationMiddleware

# When switching to a backend that stores its own data, such as FilesystemBackend, pass this same object to every place that uses it
backend = StateBackend()

agent = create_deep_agent(
    model=model,
    # No need to configure FilesystemMiddleware yourself; create_deep_agent adds it automatically with this backend
    backend=backend,
    middleware=[
        # Same name as the default summarization middleware, so it replaces it in place. trigger is required, or no automatic summarization happens
        SummarizationMiddleware(
            model=model,
            backend=backend,
            trigger=("tokens", 100000),
            keep=("messages", 6)
        ),
    ],
)
```

**Comparison with the LangChain version**

In LangChain it is Node-style and runs in `before_model` / `abefore_model`. It replaces the old messages in the current `state["messages"]` with a summary and keeps the recent messages.
In Deep Agents it is Wrap-style and runs when the model is called. It keeps the original messages, records the summary and the cutoff position separately, writes the old messages being summarized to the backend, and includes the saved path in the summary.
