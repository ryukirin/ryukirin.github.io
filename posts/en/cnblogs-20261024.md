### Chapter 8 Long-Term Memory: Giving Agents Memory Across Conversations

#### How memory works

The agent reads and writes memory as files, and you control where those files are stored with the backend

1. Prepare storage and files: configure the backend and the Store, and create the memory files to be loaded in advance
2. Load memory:
   1. `memory=` takes the paths of **existing files**, and their content goes into the system prompt
   2. `skills=` takes directories that contain skill subdirectories. Metadata is injected first, and the agent reads the body when needed
3. Update memory (optional): the prompt specifies when to write and to which file, then the agent calls tools such as `edit_file` to update it for later conversations

#### Two kinds of agent "memory"

**Short-term memory: thread-scoped**

The default StateBackend stores files in LangGraph's agent state. This is a form of short-term memory

- Persisted within one conversation thread
- Not lost across turns (through the checkpointer)
- Isolated by thread_id
  - A new thread cannot read files in an old thread's state
  - As long as the checkpointer still holds the old thread's state, going back to the old thread can read them

[Checkpointer details](#checkpointer-the-basis-of-short-term-memory)

**Long-term memory: cross-thread**

Stores information that needs to be shared between conversations

- User preferences
- Project background knowledge
- Accumulated research results
- Improved instructions the agent learned from feedback

#### Checkpointer: the basis of short-term memory

A chat app makes a good comparison: a thread is a chat window, sending a message is one invoke, and starting a new chat means switching to a new thread_id

```
Thread thread_id="a1"            ← one conversation (one chat window)
├── Turn 1 invoke("My name is Zhang San")   ← one run
│     └── model → tool → model …   ← several steps. The checkpointer saves a snapshot after each step
├── Turn 2 invoke("What's my name?")
│     └── first restores the state from a1's latest snapshot, then continues
Thread thread_id="a2"            ← another conversation, with its own state, starting empty
```

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()

agent = create_deep_agent(
    model=model,
    checkpointer=checkpointer,
)

# Within the same thread_id, the agent remembers the earlier conversation
config = {"configurable": {"thread_id": "conversation-001"}}
agent.invoke({"messages": [{"role": "user", "content": "My name is Zhang San"}]}, config=config)
agent.invoke({"messages": [{"role": "user", "content": "What is my name?"}]}, config=config)
# The agent can answer "Your name is Zhang San"

# With a different thread_id, the agent does not remember
config2 = {"configurable": {"thread_id": "conversation-002"}}
agent.invoke({"messages": [{"role": "user", "content": "What is my name?"}]}, config=config2)
# The agent does not know who you are
```

How the checkpointer works:

- After each step the agent runs, the current state is saved automatically (message history, filesystem state, the task list when Todo is enabled, and so on)
- On the next call with the same thread_id, the previous state is restored automatically
- Use MemorySaver (in memory, lost on restart) for development and PostgresSaver (database, persistent) for production

| Configuration | Result |
| --- | --- |
| No checkpointer | Every invoke is independent. There is no concept of a "thread", and nothing is kept between turns |
| Checkpointer configured, no thread_id passed | Raises an error: ValueError: Checkpointer requires one or more of the following 'configurable' keys: thread_id, ... |
| Checkpointer configured and thread_id passed | Turns with the same thread_id share one state |

**Short-term memory management strategies**

| Strategy | How | When to use |
| --- | --- | --- |
| Trim | Keep only the last N messages and drop earlier ones. To customize it, use `@before_model` middleware | Simple and blunt, for cases that do not need earlier context |
| Delete | Remove specific messages precisely with RemoveMessage | Selective cleanup (such as removing sensitive information) |
| Summarize | Compress old messages into a summary with an LLM. `SummarizationMiddleware` is built in automatically and can be overridden by one with the same name | When the meaning of the history must be kept. The most recommended approach |

Custom trimming logic

```python
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langchain.agents import AgentState
from langchain.agents.middleware import before_model
from langgraph.runtime import Runtime

@before_model
def trim_messages(state: AgentState, runtime: Runtime) -> dict | None:
    """Keep only the last few messages to prevent context overflow."""
    messages = state["messages"]
    if len(messages) <= 3:
        return None  # No trimming needed

    first_msg = messages[0]  # Keep the first message (usually the system message)
    recent = messages[-3:]   # Keep the last 3 messages
    return {
        "messages": [
            RemoveMessage(id=REMOVE_ALL_MESSAGES),
            first_msg,
            *recent,
        ]
    }

# Add it through the middleware parameter of create_agent or create_deep_agent
agent = create_deep_agent(
    model=model,
    middleware=[trim_messages],
)
```

**Advanced: custom AgentState**

Deep Agents uses DeepAgentState by default, and LangChain uses AgentState by default

|  | AgentState | DeepAgentState |
| --- | --- | --- |
| How messages are stored | add_messages: every checkpoint stores a full copy of the message list at that point, so earlier messages are stored again in every checkpoint | DeltaChannel: checkpoints do not hold the full list. Each step records only the newly added message, and reading stitches these deltas together from the start. A full snapshot is saved about every 50 steps, so reading does not have to start from the first message every time |
| Checkpoint size | Grows with the square of the step count | Grows linearly with the step count |
| Where it is used | The state_schema of create_agent, and the state_schema of custom middleware | The state_schema of create_deep_agent |

Both have three fields by default
- `messages`: message history
- `jump_to`: a field middleware uses internally to control jumps. Private and not visible from outside
- `structured_response`: structured output

Each middleware can extend the default state with its own fields. When the agent is created, these schemas are merged into the final state

| Middleware | Schema class | Fields added |
| --- | --- | --- |
| FilesystemMiddleware | `FilesystemState` | `files` (StateBackend files) |
| TodoListMiddleware | `PlanningState` | `todos` |
| SkillsMiddleware | `SkillsState` | `skills_metadata` and others |
| MemoryMiddleware | `MemoryState` | `memory_contents` |

The annotation on a field decides whether it is visible from outside:

- `OmitFromOutput`: not included in the return value of invoke
- `PrivateStateAttr`: used only inside middleware

What the checkpointer saves at every step is this whole state

A custom state adds new fields to the default state, and a field with the same name overrides the default one

```python
# Only the key code is kept. Output and building write_todos are omitted
class MyState(DeepAgentState):
    """Add two new fields to the default Deep Agents state and redeclare one existing field"""

    # New name, no reducer: a new value overwrites the old one on update
    note: NotRequired[str]

    # New name, operator.add: appended on update
    tags: NotRequired[Annotated[list[str], operator.add]]

    # Same name (already defined by TodoListMiddleware), changed to append on update
    todos: NotRequired[Annotated[list, operator.add]]
```
Output
```

State fields: ['files', 'jump_to', 'messages', 'structured_response', 'todos']
todos: ['task B']
messages count: 8

== Custom MyState
State fields: ['files', 'jump_to', 'messages', 'note', 'structured_response', 'tags', 'todos']
note  (new name, no reducer): b
tags  (new name, operator.add): ['x', 'y']
todos (same name, changed to operator.add): ['task A', 'task B']

```

Tools can read and write these custom state fields through ToolRuntime

```python
@tool
def get_note(runtime: ToolRuntime) -> str:
    """Read the current note and tags."""

    # runtime.state reads the state
    return f"Note: {runtime.state.get('note', '(none)')}, tags: {runtime.state.get('tags', [])}"

@tool
def update_note(new_note: str, runtime: ToolRuntime) -> Command:
    """Change the note to new_note."""

    # Command(update={...}) writes the state
    return Command(update={
        "note": new_note,   # Replaced as a whole
        "messages": [ToolMessage(f"Note changed to {new_note}", tool_call_id=runtime.tool_call_id)],
    })

@tool
def add_tag(tag: str, runtime: ToolRuntime) -> Command:
    """Add a tag to the current conversation."""

    # Command(update={...}) writes the state
    return Command(update={
        # operator.add appends to the old list, so pass only the new items
        "tags": [tag],
        "messages": [ToolMessage(f"Added tag {tag}", tool_call_id=runtime.tool_call_id)],
    })

agent = create_deep_agent(model=model, tools=[get_note, update_note, add_tag],
                          state_schema=MyState, checkpointer=InMemorySaver())
```

The call passes the initial values `note="a"` and `tags=["x"]`, and a scripted model runs in order: read, change `note`, add a `tag`, read again

#### CompositeBackend: the core of long-term memory

**Runtime identity and namespaces**

`StoreBackend` uses `namespace` to separate the data of different users, agents, or organizations
When deployed to LangSmith / LangGraph Server, `rt.server_info` provides the `assistant_id` and the logged-in user
For local runs or self-hosting, a custom field has to be added

```python
def assistant_namespace(rt):
    if rt.server_info:
        return (rt.server_info.assistant_id,)
    return ("local-agent",)


def user_namespace(rt):
    if rt.server_info and rt.server_info.user:
        return (rt.server_info.user.identity,)
    user_id = getattr(rt.context, "user_id", "local-user")
    return (user_id,)


def org_namespace(rt):
    org_id = getattr(rt.context, "org_id", "default-org")
    return (org_id,)
```

Every rerun of the whole script creates a new `InMemoryStore`, which keeps data only in the current process
Crossing threads requires reusing the Store, and keeping data across processes or restarts requires a persistent Store, covered later in this chapter

#### Use cases

- User preference memory: separate each user's preferences with a user-scoped namespace
- Self-improving agents: update their own instructions based on user feedback
- Knowledge base accumulation: build a knowledge base gradually over many conversations
- Ongoing research projects: the agent loads all research files at startup and updates progress after each conversation. Multiple memory paths let research continue across conversations

#### Advanced usage

**Six dimensions of memory**

| Dimension | Core question | Options |
| --- | --- | --- |
| Duration | How long is it kept? | Short-term (one conversation) / long-term (across conversations) |
| Information type | What is remembered? | Episodic memory (past experiences) / procedural memory (skills) / semantic memory (facts) |
| Scope | Who can see it? | User level / agent level / organization level |
| Update strategy | When is it written? | During the conversation (default) / between conversations (background consolidation) |
| Retrieval | How is it read? | Loaded at startup (memory=) / read on demand (skills) |
| Permissions | Can the agent write it? | Read-write (default) / read-only (shared policies) |

**Organization-level memory**

Organization-level memory is shared across all users and agents, and is usually read-only to prevent injection attacks
Use `org_namespace()` above

**Episodic memory**

Episodic memory stores complete past experiences, so the agent can recall "how a problem was solved", not only "what was learned"
The Deep Agents checkpointer supports episodic memory natively. To make past conversations searchable, wrap them in a search tool

In the original example in the course and the official docs, `query` is never used, so every search returns the same result. It also uses `get_history`, which returns a list of checkpoints, so the same conversation shows up repeatedly across checkpoints. The version below matches keywords literally, the same way the grep tool built into Deep Agents does

```python
from langchain.tools import tool, ToolRuntime
from langgraph_sdk import get_client

client = get_client(url="<DEPLOYMENT_URL>")


def current_user_id(runtime: ToolRuntime) -> str:
    if runtime.server_info and runtime.server_info.user:
        return runtime.server_info.user.identity
    user_id = getattr(runtime.context, "user_id", None)
    if user_id:
        return user_id
    raise ValueError("user_id must be provided in server_info or runtime.context")


@tool
async def search_past_conversations(query: str, runtime: ToolRuntime) -> str:
    """Find messages containing the keyword query in this user's past conversations. Matching is literal, so if nothing is found, search again with a synonym, English, or a shorter keyword."""
    user_id = current_user_id(runtime)
    current_thread = runtime.config.get("configurable", {}).get("thread_id")
    threads = await client.threads.search(
        metadata={"user_id": user_id},
        limit=5,
        sort_by="updated_at",  # The API docs do not specify a default order, so set it explicitly
        sort_order="desc",
    )
    keyword = query.strip().lower()
    if not keyword:
        return "query must not be empty. Pass the keyword to look for and call again."
    hits = []
    for thread in threads:
        if thread["thread_id"] == current_thread:
            # Skip the conversation in progress
            continue
        # get_state returns only the current state, without the duplicates get_history has
        state = await client.threads.get_state(thread_id=thread["thread_id"])
        for message in state["values"].get("messages", []):
            content = str(message.get("content", ""))
            if keyword in content.lower():
                hits.append(f"[{thread['thread_id']}] {message.get('type')}: {content[:300]}")
    return "\n".join(hits[:10]) or f"No past conversation containing '{query}' was found."
```

Notes

- `threads.search()` can only filter threads by metadata, status, and similar conditions. It does not accept a text query, so message bodies are matched on the client
- The search term comes from the model, so only content with the same wording is found. For example, a search for "error" will not find a conversation that only says "KeyError", so the tool description tells the model to search again with different words
- The `user_id` in a thread's `metadata` is written by the application when it creates the thread. The server does not add it, and without it no threads are found
- The current thread is usually the most recently updated one and counts toward the 5, so usually only 4 past threads are found
- For semantic search, write conversation summaries into a Store with semantic search enabled (configure `store.index` in `langgraph.json`), then query with `client.store.search_items(namespace, query=query)`

**Background consolidation**

By default, the agent writes memory in real time during the conversation (the hot path). The other mode processes it in the background between conversations: a separate "consolidation agent" is deployed to review recent conversations, extract key facts, and merge them into the memory store
For the code, see
[the consolidation agent example](https://datawhalechina.github.io/deepagents-in-action/chapters/ch08-long-term-memory/#%E5%90%8E%E5%8F%B0%E8%AE%B0%E5%BF%86%E6%95%B4%E5%90%88background-consolidation)
The `query: str` of `search_recent_conversations` is not needed

**Concurrent writes**

For agent-level or organization-level memory, consider serializing writes through background consolidation, or splitting memory into separate files by topic to reduce conflicts

- Split files by topic: keep `/memories/preferences.md`, `/memories/project/tech-stack.md`, and `/memories/research/sources.md` separate to lower the chance that several threads edit the same file at once
- Append records, then merge in the background: during the conversation, write to an append-only log such as `/memories/events/2026-xx-xx-thread-id.md` first, and let a background consolidation agent periodically deduplicate and merge it into stable memory files
- Let only background tasks write shared memory: keep agent-level and organization-level memory read-only where possible. Ordinary conversations only submit candidate updates, and a background consolidation task reviews and writes them one at a time
- Add approval for sensitive memory: for organization policies, security rules, or overwriting long-term preferences, use permissions or human-in-the-loop to block direct overwrites without confirmation

### Chapter 9 Human-in-the-Loop: Building Safe Human-Agent Collaboration

Human-in-the-loop (HITL): the agent pauses before specific operations, waits for a human to approve, edit, reject, or respond directly, and then continues

#### Configuring `interrupt_on`

```python
from deepagents import create_deep_agent
from langgraph.checkpoint.memory import MemorySaver

# Tool and model definitions are omitted

# A checkpointer is required for HITL
checkpointer = MemorySaver()

agent = create_deep_agent(
    model=model,
    tools=[delete_file, read_file, send_email],
    interrupt_on={
        # allowed_decisions specifies the available actions
        # The actions are approve / edit / reject / respond
        "delete_file": {"allowed_decisions": ["approve", "edit", "reject"]},
        "read_file": False,    # No interrupt
        "send_email": {"allowed_decisions": ["approve", "reject"]},  # Approve or reject only, no editing
    },
    checkpointer=checkpointer,  # Required!
)
```

| Decision | Meaning | Scenario |
| --- | --- | --- |
| approve | Approve and run with the original arguments the agent proposed | "Confirm deleting this file" |
| edit | Run after editing the arguments | "Change the recipient before sending" |
| reject | Skip this tool call and send the reason back to the agent | "Don't delete it, cancel" |
| respond | Do not run the tool. Return the human's message as a successful synthetic tool result | Tools that "ask the user", such as `ask_user` |

Subagents can have their own `interrupt_on` configuration, which overrides the main agent's settings
When a subagent performs sensitive operations, it can be set to interrupt and ask for confirmation

#### Conditional interrupts: stopping only the truly dangerous calls

```python
from deepagents import create_deep_agent
from langchain.agents.middleware import ToolCallRequest
from langgraph.checkpoint.memory import MemorySaver


def writes_outside_workspace(request: ToolCallRequest) -> bool:
    """Pause only when writing to a path outside the workspace."""
    path = request.tool_call["args"].get("file_path", "")
    return not path.startswith("/workspace/")


agent = create_deep_agent(
    model=model,
    interrupt_on={
        "write_file": {
            "allowed_decisions": ["approve", "edit", "reject"],
            # Pause only when this returns True. Run when False
            "when": writes_outside_workspace,
        },
    },
    checkpointer=MemorySaver(),
)
```

#### Interrupt and resume

When the agent calls a tool with an interrupt configured during a run, the run is interrupted and the interrupt information is returned
After the user decides based on that information, the run is resumed with the thread_id

```python
import uuid
from langgraph.types import Command

# Create a thread_id (the same one must be used to resume)
config = {"configurable": {"thread_id": str(uuid.uuid4())}}

# Step 1: send the request
result = agent.invoke(
    {"messages": [{"role": "user", "content": "Delete the file temp.txt"}]},
    config=config,
    version="v2",
)

# Step 2: check for an interrupt
if result.interrupts:
    interrupt_value = result.interrupts[0].value
    action_requests = interrupt_value["action_requests"]
    review_configs = interrupt_value["review_configs"]
    config_map = {cfg["action_name"]: cfg for cfg in review_configs}

    # Show it to the user
    for action in action_requests:
        review_config = config_map[action["name"]]
        args = action.get("arguments", action.get("args", {}))
        print(f"Tool: {action['name']}")
        print(f"Args: {args}")
        print(f"Allowed decisions: {review_config['allowed_decisions']}")

    # Step 3: the user decides
    # message can be predefined (the message for a rejection) or typed by the user
    decisions = [
        {"type": "approve"}  # The user approves the deletion
    ]
    # decisions = [{
    #     "type": "reject",
    #     "message": "The user declined to delete this file. Do not try to delete it again. Ask whether to archive it instead.",
    # }]

    # Step 4: resume (the same config is required!)
    result = agent.invoke(
        Command(resume={"decisions": decisions}),
        config=config,     # Same thread_id
        version="v2",
    )

# Get the final result
print(result.value["messages"][-1].content)
```

When the user returns `reject`, Deep Agents skips that tool call and sends the rejection feedback back to the agent
For sensitive tools (such as deletion), the feedback should say explicitly not to request the deletion again and to switch to another operation

#### Handling interrupts for multiple tool calls

```python
# User request: "Delete temp.txt and email admin"
result = agent.invoke(
    {"messages": [{"role": "user", "content": "Delete temp.txt and email admin@example.com about it"}]},
    config=config,
    version="v2",
)

if result.interrupts:
    action_requests = result.interrupts[0].value["action_requests"]
    # action_requests[0] = delete_file(path="temp.txt")
    # action_requests[1] = send_email(to="admin@example.com", ...)

    # Provide decisions in order
    decisions = [
        {"type": "approve"},  # Approve the deletion
        {
            "type": "reject",
            "message": "The user declined to send the email. Do not retry this send.",
        },
    ]

    result = agent.invoke(
        Command(resume={"decisions": decisions}),
        config=config,
        version="v2",
    )
```
The number and order of decisions must match. `decisions` must correspond one-to-one with `action_requests`, in the same order

#### Recommended interrupt settings by risk level

| Risk level | Tool type | Configuration | Reason |
| --- | --- | --- | --- |
| High | Delete, overwrite, send, deploy | `approve`/`edit`/`reject` | The operation is irreversible or affects external systems. Avoid `respond` being mistaken for a successful result |
| Medium | Write, external calls | `approve`/`reject` | Needs approval but no argument editing |
| Low | Read, search, list | `False` | Read-only, safe, and without side effects |
| Human input | Ask for preferences, fill in missing information | `respond` | The tool exists for a human to answer, so the human's `message` becomes a successful tool result |

#### The filesystem `mode="interrupt"`

```python
    permissions=[
        FilesystemPermission(
            operations=["write"],

        ),
    ],

```

### Human approval before writes

`protected_path` in `agent.py` decides which paths need approval:

```python
def protected_path(request):
    """Define the paths whose operations need approval"""
    path = request.tool_call["args"].get("file_path", "")
    try:
        path = validate_path(path)
    except ValueError:
        return False
    return path.startswith(("/history/", "/report/"))
```

- `interrupt_on` sets `when=protected_path` for `write_file`, `edit_file`, and `delete`, so the run pauses only when the target is under `/history/` or `/report/`. Writes to other paths (including `/memories/`) do not pause
- `protected_path` first normalizes the path with `validate_path`. If normalization fails, it returns `False` and the run does not pause
- `allowed_decisions` allows only `approve` and `reject`
- Write calls made inside subagents pause as well
- Resuming requires the same `thread_id`, so a `MemorySaver` checkpointer was added, and each run generates a new `thread_id` with `uuid4`

When the run pauses, `ask_decision` in `ask_user.py` reads the decision from the command line:

```python
import json

def ask_decision(action, allowed):
    name = action["name"]
    args = action.get("arguments", action.get("args", {}))
    print(f"\nTool: {name}\nArgs: {json.dumps(args, ensure_ascii=False)}\nAllowed decisions: {', '.join(allowed)}")
    while True:                                    # Ask again if the input is not allowed
        choice = input("Enter a decision: ").strip()
        if choice in allowed:
            break
        print(f"Enter one of {', '.join(allowed)}")

    if choice == "approve":
        return {"type": "approve"}
    if choice == "edit":                           # Ask for each argument. Press Enter to keep the original value
        new_args = {}
        for key, value in args.items():
            text = input(f"  {key} (press Enter to keep {value!r}): ").strip()
            new_args[key] = text if text else value
        return {"type": "edit", "edited_action": {"name": name, "args": new_args}}
    if choice == "reject":                         # The reason can be left empty. If empty, the middleware's default feedback is used
        decision = {"type": "reject"}
        reason = input("Reason for rejection (optional): ").strip()
        if reason:
            decision["message"] = reason
        return decision
    return {"type": "respond", "message": input("Answer: ").strip()}
```

- Input that is not in `allowed_decisions` is asked for again
- After `reject`, a reason can be entered, and it is returned to the model as `message`. If it is empty, the middleware's default feedback is used
- The `edit` and `respond` branches are not used right now, because `allowed_decisions` does not include them

### Agent

The part of `agent.py` that creates and runs the agent:

```python
with SqliteStore.from_conn_string("news.db") as store:
    store.setup()  # Creates the tables on the first run. Later calls do not create them again

    # Create a thread ID for resuming after an interrupt
    configurable = {"configurable": {"thread_id": str(uuid.uuid4())}}

    agent = create_deep_agent(
        model=model,
        # Define tools
        tools=[internet_search, get_current_time],
        # Define the system prompt
        system_prompt=config.SYSTEM_PROMPT,
        # Define middleware explicitly
        middleware=[TodoListMiddleware()],
        # Custom context
        context_schema=MemoryContext,
        # Define the memory file path
        memory=["/memories/preferences.md"],
        # Use SqliteStore as persistent storage
        store=store,
        # Define the backend storage. CompositeBackend combines several backends
        backend=CompositeBackend(
            default=StateBackend(),            # Default: temporary storage
            # Routes
            routes={
                "/history/": StoreBackend(
                    namespace=lambda rt: (*user_namespace(rt), "history"),
                ),
                "/memories/": StoreBackend(
                    namespace=lambda rt: (*user_namespace(rt), "memories"),
                ),
                "/report/": StoreBackend(
                    namespace=lambda rt: (*user_namespace(rt), "report"),
                ),
                "/skills/": FilesystemBackend(root_dir="skills", virtual_mode=True),
            }
        ),
        # Put writes to files under history and report in interrupt mode to prevent mistakes
        interrupt_on={
            "write_file": {
                "allowed_decisions": ["approve", "reject"], 
                "when": protected_path
            }, 
            "edit_file": {
                "allowed_decisions": ["approve", "reject"], 
                "when": protected_path
            }, 
            "delete": {
                "allowed_decisions": ["approve", "reject"], 
                "when": protected_path
            },
        },
        # Define permissions
        permissions=[
            # Make skills read-only
            FilesystemPermission(
                operations=["write"],
                paths=["/skills/**"],
                mode="deny",
            ),
        ],
        # Resuming after an interrupt needs a checkpointer to track the thread ID
        checkpointer=MemorySaver(),
        # Define the subagent list
        subagents=subagents,
    )

    result = agent.invoke(
        {"messages": [{"role": "user", "content": config.USER_PROMPT}]},
        config=configurable,
        version="v2",
    )

    while result.interrupts:
        interrupt_value = result.interrupts[0].value
        action_requests = interrupt_value["action_requests"]
        review_configs = interrupt_value["review_configs"]
        config_map = {cfg["action_name"]: cfg for cfg in review_configs}

        # Provide decisions in order
        decisions = []
        for action in action_requests:
            review_config = config_map[action["name"]]
            args = action.get("arguments", action.get("args", {}))
            decisions.append(ask_decision(action, review_config["allowed_decisions"]))

        result = agent.invoke(
            Command(resume={"decisions": decisions}),
            config=configurable,
            version="v2",
        )

print(result.value["messages"][-1].content)
```

- `create_deep_agent` gained `context_schema`, `memory`, `store`, `interrupt_on`, and `checkpointer`. The `/report/` route changed from `FilesystemBackend` to `StoreBackend`, and a `/memories/` route was added
- `invoke` now passes `version="v2"`, and `result.interrupts` tells whether the run paused. On a pause, the run resumes with `Command(resume={"decisions": decisions})` and the same `configurable`, until there are no more interrupts
- `MemorySaver` keeps the interrupt state only in process memory. If the program exits during a pause, that run cannot be resumed
- The resume loop handles only the first interrupt in `result.interrupts`. When several subagents write in parallel and raise several interrupts at once, LangGraph requires a resume value for each interrupt ID, and the current code raises an error
