### Chapter 7 Skills: Reusable Capability Packages for Agents

#### Skill directory structure

```
skills/
└── langgraph-docs/
    ├── SKILL.md              # Required: metadata + instructions
    ├── scripts/              # Optional: executable scripts
    │   └── fetch_docs.py
    ├── references/           # Optional: detailed docs
    │   ├── api-patterns.md
    │   └── style-guide.md
    └── assets/               # Optional: templates, data files
        ├── report-template.md
        └── schema.json
```

| Directory     | Purpose                                              | When it is loaded                                                                  |
| ------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `SKILL.md`    | Metadata + core instructions                         | The metadata goes into the prompt at startup. The agent reads the body when needed |
| `scripts/`    | Executable scripts (Python, Bash, JS, and so on)     | Run by the agent when the instructions call for it                                 |
| `references/` | Detailed reference docs (API patterns, style guides) | Read by the agent when it needs more detail                                        |
| `assets/`     | Templates, data files, schemas, and other static resources | Read by the agent when needed                                                |

#### Structure of `SKILL.md`

It has a YAML frontmatter and a Markdown body (the instructions)

**YAML frontmatter**


| Field         | Required | Description                                                                                      |
| ------------- | -------- | ------------------------------------------------------------------------------------------------ |
| name          | Yes      | Lowercase letters, digits, and hyphens, 1-64 characters. Must match the parent directory name.   |
| description   | Yes      | What the skill does and when to use it. Up to 1024 characters.                                   |
| license       | No       | License name                                                                                     |
| compatibility | No       | Environment requirements (for example, network access or a specific CLI tool). Up to 500 characters. |
| metadata      | No       | Arbitrary key-value pairs (author, version, entrypoint, and so on)                               |
| allowed-tools | No       | Space-separated list of pre-approved tools                                                       |

**description is the most important field**

- A good description: has specific, clear trigger conditions
- A bad description: is vague and has no trigger signals

A bad description causes two problems: the skill is not matched when it should be (missed recall), and it is triggered when it should not be (false recall)

#### Progressive Disclosure

Skills do not hand everything to the model at once, which would fill the context with noise. Progressive disclosure splits a skill into three levels and gives them to the model only when needed.

| Level                 | What is loaded                                         | When                                                       | Handled by                                            |
| --------------------- | ------------------------------------------------------ | ---------------------------------------------------------- | ----------------------------------------------------- |
| Level 1: Metadata     | `name` + `description` + file path                     | At agent startup, the metadata of discoverable skills is loaded | `SkillsMiddleware`                               |
| Level 2: Instructions | The body of `SKILL.md`                                 | When the agent decides it is relevant and calls `read_file` | The LLM decides, and reads it through the file system tools |
| Level 3: Resources    | Files under `scripts/`, `references/`, and `assets/`  | When the instructions refer to a file                      | The LLM decides on its own whether to read them       |

How it works:

- **Startup**: `SkillsMiddleware` scans the skill subdirectories under the configured directories, extracts `name` and `description` from each `SKILL.md` frontmatter, and puts them in the system prompt

- **Reading**: `SkillsMiddleware` provides the list of available skills and instructions on how to read them. After the user sends a request, the agent uses the `description` to decide whether it needs a skill, then reads the corresponding `SKILL.md` with `read_file` and puts the body into the context.

- **Execution**: The agent follows the instructions in the body. If the instructions refer to files under `references/` or `assets/`, the agent decides on its own whether to read them. This step is controlled by the LLM, and the middleware no longer intervenes.

#### Multiple skill sources and precedence

Paths are passed to the `skills` argument of `create_deep_agent`

```python

    model=model,
    backend=backend,
    skills=[path1,...],
)
```

When several paths contain a skill with the same name, later paths override earlier ones

Suppose project rules take precedence over team rules


Then pass them like this

#### Usage

Deep Agents provides three backends for loading skills, each with a different file storage strategy.

**Basic usage (FilesystemBackend)**

Reads skill files directly from the local disk. Suited to local development and CLI use

```python
from deepagents import create_deep_agent
from deepagents.backends.filesystem import FilesystemBackend

backend = FilesystemBackend(root_dir="./my-project", virtual_mode=True)

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    backend=backend,
    # Parent directories of the skill subdirectories. More than one is allowed
    # Use forward slashes / in paths
    skills=["/skills/"],
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is LangGraph?"}]},
    config={"configurable": {"thread_id": "1"}},
)
```

**StateBackend: injecting skills through state**

StateBackend stores files in the LangGraph agent state. It suits environments without a disk (such as serverless deployments) or cases where skill content is injected dynamically
Virtual paths must start with / (absolute path format)


```python
from urllib.request import urlopen
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.backends.utils import create_file_data
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
backend = StateBackend()

# Load the skill remotely (it can also be read locally)
skill_url = "https://raw.githubusercontent.com/langchain-ai/deepagents/refs/heads/main/libs/code/examples/skills/langgraph-docs/SKILL.md"
with urlopen(skill_url) as response:
    skill_content = response.read().decode('utf-8')

# The content must be formatted with create_file_data()
skills_files = {
    "/skills/langgraph-docs/SKILL.md": create_file_data(skill_content),
}

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    backend=backend,
    skills=["/skills/"],
    checkpointer=checkpointer,
)

result = agent.invoke(
    {
        "messages": [{"role": "user", "content": "What is langgraph?"}],
        # Injected through the files argument. It has to be passed on every call
        "files": skills_files,  
    },
    config={"configurable": {"thread_id": "12345"}},
)
```

**StoreBackend: persistence across threads**

StoreBackend persists files in a LangGraph Store. A file written once is available to all threads, so a skill written once can be read in every session.

```python
from urllib.request import urlopen
from deepagents import create_deep_agent
from deepagents.backends import StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
# The namespace argument is a function that takes the runtime config and returns a namespace tuple
backend = StoreBackend(namespace=lambda _rt: ("filesystem",))

skill_url = "https://raw.githubusercontent.com/langchain-ai/deepagents/refs/heads/main/libs/code/examples/skills/langgraph-docs/SKILL.md"
with urlopen(skill_url) as response:
    skill_content = response.read().decode('utf-8')

# Inject the file here so it does not have to be passed on every invoke
store.put(
    namespace=("filesystem",),
    key="/skills/langgraph-docs/SKILL.md",
    value=create_file_data(skill_content),
)

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    backend=backend,
    store=store,
    skills=["/skills/"],
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is langgraph?"}]},
    config={"configurable": {"thread_id": "12345"}},
)
```

About `namespace`:
- `namespace` is a "drawer" in the Store. It decides who a piece of data is shared with and who it is isolated from
- `namespace` is a tuple because it is hierarchical
- Every item in the Store has a two-part address, `(namespace, key)`, meaning which file in which drawer (the file path without the route prefix `/memories/`)
- `namespace` is written as a function here so that arguments can route data to different namespaces
  ```python
  # Different user_id values lead to different namespaces
  # rt is short for runtime
  # rt.context.user_id is
  # declared with agent = create_deep_agent(...,context_schema=TenantContext)
  # and passed in on each invoke(..., context=UserContext(user_id=...))
  # UserContext is a dataclass you define yourself
  lambda rt: ("users", rt.context.user_id)
  ```
  This is equivalent to
  ```python
  def pick_namespace(rt):
    return ("users", rt.context.user_id)
  ```
- Chapter 8 covers this in detail

**Loading skills dynamically at runtime**

Different skill sets can be loaded based on the user's role, the tenant, or the request type
- By user role: engineers see code-related skills, and the data team sees analysis skills
- By tenant configuration: in SaaS, different customers enable different skill packages

#### Skill permissions

In production, skill permissions involve three dimensions:

- Visibility: whether the agent can discover and read a skill
- Write access: whether the agent can modify a skill file
- Approval: whether a write needs human confirmation

**Read-only skills (enterprise knowledge base)**

Combine `FilesystemPermission` with `CompositeBackend` to deny `write` access to the `skills` folder

```python
from dataclasses import dataclass

from deepagents import FilesystemPermission, create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.store.memory import InMemoryStore

# Store each tenant's organization ID
@dataclass(frozen=True)
class TenantContext:
    org_id: str

def org_skill_namespace(rt):
    # Read rt.context.org_id
    # Return "default-org" if there is no org_id
    org_id = getattr(rt.context, "org_id", "default-org")
    return ("curated-skills", org_id)

store = InMemoryStore()
store.put(
    # This skill is only for "org-acme"
    namespace=("curated-skills", "org-acme"),
    # /skills/ is the CompositeBackend mount prefix. Inside the Store, paths are relative to the route.
    key="/test-skill/SKILL.md",
    value=create_file_data("""---
name: test-skill
description: Used to verify that a read-only skill can be discovered and loaded.
---

# test-skill
"""),
)

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    # Define the structure of context
    context_schema=TenantContext,
    backend=CompositeBackend(
        default=StateBackend(),
        # Switch the namespace for operations on "/skills/"
        routes={
            "/skills/": StoreBackend(
                namespace=org_skill_namespace,
            ),
        },
    ),
    skills=["/skills/"],
    permissions=[
        FilesystemPermission(
            # write_file, edit_file, and delete are all denied
            operations=["write"],
            paths=["/skills/**"],
            mode="deny",
        ),
    ],
    store=store,
)

agent.invoke(
    {"messages": [{"role": "user", "content": "List the available skills"}]},
    # Pass context at call time
    context=TenantContext(org_id="org-acme"),
    config={"configurable": {"thread_id": "1"}},
)
```

**Writes need approval (interrupt mode)**

The agent can propose changes, but they take effect only after a person approves them

```python
from deepagents import FilesystemPermission, create_deep_agent
from langgraph.checkpoint.memory import MemorySaver

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    skills=["/skills/personal/"],
    permissions=[
        FilesystemPermission(
            operations=["write"],
            paths=["/skills/**"],
            mode="interrupt",
        ),
    ],
    checkpointer=MemorySaver(),  # interrupt requires a checkpointer
)
```
- `interrupt` mode relies on the checkpointer to save the paused state, so `MemorySaver` or another persistent checkpointer is required
- This feature requires `deepagents>=0.6.8`
- In LangGraph Studio, `interrupt` is rendered as an approval UI automatically. When calling through the API, the client has to poll the state and submit the approval result

**Shared + personal skill layers**

The most common deployment pattern has two layers: a read-only skill library shared by the team, plus a writable personal skill space for each user

```python
from dataclasses import dataclass
from langchain_openai import ChatOpenAI
from deepagents import FilesystemPermission, create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from deepagents.backends.utils import create_file_data
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore
# My own file, used to pass in the keys from .env and other settings
import config

@dataclass(frozen=True)
class TenantContext:
    org_id: str
    user_id: str

def shared_skill_namespace(rt):
    org_id = getattr(rt.context, "org_id", "default-org")
    return ("curated-skills", org_id)

def personal_skill_namespace(rt):
    if rt.server_info and rt.server_info.user:
        return ("user-skills", rt.server_info.user.identity)
    user_id = getattr(rt.context, "user_id", "local-user")
    return ("user-skills", user_id)

store = InMemoryStore()

# Load the shared skills and the personal skills
store.put(
    # Only for org-acme
    namespace=("curated-skills", "org-acme"),
    key="/team-report/SKILL.md",
    value=create_file_data("---\nname: team-report\ndescription: Daily report format shared by the team\n---\n\n# team-report\n")
)
store.put(
    # Only for alice
    namespace=("user-skills", "alice"),
    key="/my-notes/SKILL.md",
    value=create_file_data("---\nname: my-notes\ndescription: alice's personal note format\n---\n\n# my-notes\n")
)

model = ChatOpenAI(
    model=config.MODEL_NAME, 
    api_key=config.DEEPSEEK_API_KEY, 
    base_url=config.BASE_URL,
)

agent = create_deep_agent(
    model=model,
    context_schema=TenantContext,
    backend=CompositeBackend(
        default=StateBackend(),
        routes={
            "/skills/shared/": StoreBackend(
                namespace=shared_skill_namespace,
            ),
            "/skills/personal/": StoreBackend(
                namespace=personal_skill_namespace,
            ),
        },
    ),
    skills=["/skills/shared/", "/skills/personal/"],
    permissions=[
        FilesystemPermission(
            operations=["write"],
            paths=["/skills/shared/**"],
            mode="deny",
        ),
    ],
    store=store,
    checkpointer=InMemorySaver(),
)

# Thread ID. get_state uses it to find the state saved by this run
config = {"configurable": {"thread_id": "t1"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "List the available skills"}]},
    context=TenantContext(org_id="org-acme", user_id="alice"),
    config=config
)
print(result["messages"][-1].content)

# Read the full state of thread t1, including skills_metadata, which the invoke return value does not have
values = agent.get_state(config).values
for s in values.get("skills_metadata") or []:
    print(s["name"], "|", s["path"], "|", s["description"])
print("Load errors:", values.get("skills_load_errors"))
```

#### Running code with skills

**Sandbox scripts**

If skill files are stored outside the sandbox (for example, with StateBackend), a custom middleware has to sync files before and after the agent runs:

- `before_agent`: upload the skill scripts to the sandbox environment
- `after_agent`: download the output files from the sandbox

This pattern suits tasks such as data processing, API calls, and file conversion, while keeping execution safely isolated

**Interpreter skills**

Interpreter skills expose the code modules in a skill to the agent's code interpreter environment
The agent can import tested helper functions directly instead of regenerating the logic every time
The QuickJS middleware has to be installed in advance

Making a skill importable takes three steps:

- Specify the entry file (JS/TS) in `metadata.entrypoint` in the frontmatter
- Configure `CodeInterpreterMiddleware` to use the same backend
- The agent imports it in code with `await import("@/skills/<name>")`

[Example code](https://datawhalechina.github.io/deepagents-in-action/chapters/ch07-skills/#%E8%A7%A3%E9%87%8A%E5%99%A8%E6%8A%80%E8%83%BDinterpreter-skills)

#### Skills, Memory, and Tools compared


|              | Skills                                              | Memory (`AGENTS.md`)                     | Tools                                                              |
| ------------ | --------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------ |
| Purpose      | Domain capabilities loaded on demand (progressive disclosure) | Persistent context loaded at startup | Programmatic operations the agent can call                     |
| When loaded  | Read only when the agent decides they are relevant  | Loaded when the agent starts             | Available on every turn                                            |
| Format       | `SKILL.md` in a named directory                     | `AGENTS.md` file                         | Functions bound to the agent                                       |
| Precedence   | Later ones override earlier ones (last wins)        | User level + project level merged        | Defined at creation                                                |
| Best for     | Task-specific instruction sets that may be large    | Global rules and preferences that always apply | When the agent needs to perform actions, or has no file system |

#### Skill best practices

- Keep `description` short: `Use when {specific use case}. {One-sentence summary}`
- Keep the body of `SKILL.md` within 5000 tokens / 500 lines, and put details in `references/` to load when needed
- Structure it for the agent, not for people
  - Step-by-step process: explicit 1-2-3 steps instead of paragraphs
  - Decision criteria: how to choose at a branch (if X then A, else B)
  - Input/output examples (I think they should be as general as possible)
  - Edge cases: how to handle common exceptions
- Keep the number of skills under control

#### Thoughts

This was my first time seeing access permissions applied to skills. In real engineering, keeping skill packages separate from each other makes later maintenance easier and keeps the impact of changes small.

## Practice: Moving the AI news assistant's deduplication and past-news check into skills

Among the four subagents split out in Task4, news-categorizer and old-news-checker had their criteria written in the system_prompt, only a few sentences long. After Chapter 7, the rules for deduplication and the past-news check went into two skills, one for each subagent, and the system_prompt keeps only the role and the input and output.

Repository: [ryukirin/ai-news-deep-agent](https://github.com/ryukirin/ai-news-deep-agent)

### Skill directories and assignment

```text
skills/
├── news-categorizer/
│   └── news-dedup/
│       └── SKILL.md      ← loaded by news-categorizer
└── old-news-checker/
    └── history-check/
        └── SKILL.md      ← loaded by old-news-checker
```

| Subagent         | Skill           | What it specifies                                                                       |
| ---------------- | --------------- | --------------------------------------------------------------------------------------- |
| news-categorizer | `news-dedup`    | Steps for deduplicating the current list, examples of what counts as a duplicate, edge cases |
| old-news-checker | `history-check` | Steps for comparing with `/history/news_history.txt`, the history format, examples, edge cases |

- Subagents do not inherit the main agent's skills, so each of the two subagent definitions sets its source directory in `skills`. The source directories are split by subagent name, so news-categorizer loads only `news-dedup` and old-news-checker loads only `history-check`
- `/skills/` is routed to the project's `skills/` directory (`FilesystemBackend`), and `FilesystemPermission` denies writes to `/skills/**`. The subagents set no `permissions` of their own and inherit this rule, so the skills are read-only for every agent

### `SKILL.md`

`news-dedup`:

```markdown
---
name: news-dedup
description: Use when checking whether the current news article list contains duplicate news. Removes duplicate news from the current news article list.
---

# news-dedup

## Steps

1. Compare the articles in the current news article list and check for duplicate or similar news content.
2. If the current news article list contains duplicate news content, delete the lower-quality duplicates from the list.
3. Return a structured news article list with no duplicates.

## Examples
News 1: Company A announced new product X, expected to launch next month.
News 2: Company A's X is scheduled to launch next month. Its features and functions are also described.
Both items belong to the same news and should be treated as duplicates. Under the rule of removing the lower-quality item, news 2 has richer content, so keep news 2 and delete news 1.

News 3: Company A's X. Its market positioning and sales strategy are also described in detail.
This item is similar to news 1 and news 2 but has a different focus, so it is not treated as a duplicate.

News 4: The features and functions of Company A's new product X.
This item needs to be compared with news 1 and news 2. If the content is highly similar and the focus is the same, it should also be treated as a duplicate. If the quality is about the same, keep any one of them at random.

## Edge cases

- If the current news article list is empty, return an empty list.
- If every item in the current news article list duplicates another, return a single news article.
- If the current news article list has only one item, return it as is.
```

`history-check`:

```markdown
---
name: history-check
description: Use when checking whether the current news article list contains past news from /history/news_history.txt. Removes past news from the current news article list.
---

# history-check

## Steps

1. Read the list of past news from the /history/news_history.txt file.
2. Compare the articles in the current news article list with the list of past news and check for duplicate or similar news content.
3. If an article in the current news article list duplicates any item in the list of past news, delete it from the news article list.
4. After all checks are done, append the non-duplicate articles in the current news article list to the /history/news_history.txt file to keep the list of past news complete.
5. Return a structured news article list with no past news.

## news_history.txt format
One news item per line, in this format:
date | title | summary

## Examples
Past news: Company A announced new product X, expected to launch next month.
News 1: Company A's X is scheduled to launch next month.
News 2: Company A's X.
All three items belong to the same news and should be treated as duplicates.

News 4: The features and functions of Company A's new product X.
This item needs to be compared with the past news. If the content is highly similar and the focus is the same, it should also be treated as a duplicate.

## Edge cases

- If the current news article list is empty, return an empty list.
- If the /history/news_history.txt file does not exist or is empty, create it, append the current news article list to it, and return the current news article list.
- If every item in the current news article list duplicates the list of past news, return an empty list.
```
